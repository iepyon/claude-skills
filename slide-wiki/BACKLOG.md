# slide-wiki 機能バックログ

Markdown のデッキを**リンクで辿れるスライド Wiki** にする。同じデッキを PPTX と HTML にも出し、
座標は3系統で共通のレイアウトエンジンが計算する。このバックログは2つの軸で並べる —
**何が主題か**（Wiki が主題、PPTX と HTML は同じデッキの別の出し方）と、
**どう壊れるか**（黙って間違う > 見えて壊れる > 不便）。前者が band を分け、後者が band の中を並べる。
判断の根拠は[並べ方](#並べ方)にある。

  そのあと記述を実測で突き合わせ、[B-38](#b-38) と [B-25](#b-25) を実装して畳み、
  [B-45](#b-45) を積んだ）
- 起点: 2026-08-07 の調査（標準の document-skills:pptx との機能差）、
  2026-08-08 の調査（オントロジー観点のレビュー + 動作確認）、

どの緑のチェックにも出てこない — 死んだ参照は `collectRefs` に届かないので `broken` にも入らず、
未解決リンクの一覧にすら現れない。[B-44](#b-44) はこの数を数えて初めて見つかった。

いる）。問題は、緑のチェックが**見ていない範囲**が広いこと — その範囲を項目として持っているのが
[B-32](#b-32) / [B-33](#b-33) である。

**Wiki の層はその「見ていない範囲」の中にほぼ全部ある。** 今回の調査で分かったのは、
`ontology.yaml` が宣言しているのは**1つの md ファイルの中の構造だけ**で、デッキの集合・
デッキ名・`[[deck/slide]]`・ID の一意性といった**サイトの階層は1つも宣言されていない**こと
（[B-41](#b-41)）。宣言が無い層では lint も selfcheck も立てようがないので、そこで起きる
食い違い — 効かない場所のリンク（[B-39](#b-39)）、デッキ名の二重の語彙（[B-40](#b-40)）—
は**どれも緑のまま通る**。

**ただし「宣言が無いと検査が立たない」は言いすぎだった。** 畳んだ [B-38](#b-38)（明示 ID の衝突）は
このリストの1件目だったが、宣言を広げずに lint 1本で赤くできた — ID の一意性は
**デッキ内で閉じている**ので、`lint.ts` が既に立っているトークン層でそのまま見える。
サイトの階層の宣言が要るのは、**デッキをまたぐもの**（[B-40](#b-40) の deck slug、
[B-39](#b-39) の効く場所）に限られる。

## 並べ方

改名のときは「Wiki が主題か、PPTX の話か」で並べ替えた。**主題の中での順位はまだ付いていなかった** —
Wiki の項目が P0 に3つ並んでいるだけで、どれが先かは書かれていなかった。今回の調査でその中身が
見えたので、band の意味を次のように決め直す。

| band | 意味 |
|---|---|
| **P0** | **リンクの層**。この道具の看板そのもの。宣言・実装・報告の3つに分かれるが、直す対象は1つ |
| **P1** | 主題を**実際に読み書きする人が踏む**もの。読めない・書けない・気づけない |
| **P2** | 読み書きする人には見えないが、直さないと**上の band が繰り返し生えてくる**土台 |
| **P3** | 主題の外。やっても Wiki は良くならない（が、捨てるほどでもない） |

順位を決めたのは主に**壊れ方**である。この調査で分かったのは、Wiki の層の不具合が
そろって「**黙って、動いているように見える形で**壊れる」ことだった —
リンクが生の文字で出る（[B-22](#b-22)）、リンクが**別のスライドに繋がる**（畳んだ [B-38](#b-38)）、
デッキが**どこにも書かれていない名前**になる（[B-40](#b-40)）。どれも exit 0 で、lint も緑である。

**黙って間違う > 見えて壊れる > 不便**、の順に置いた。折れたリンク（[B-36](#b-36)）が
P0 の中で最後なのは、それが唯一**サイドバーに出る＝見える**壊れ方だからで、
軽いからではない。

## P0 — リンクの層（宣言も実装も報告も欠けている）

Wiki を主題にした以上、この道具の看板は `[[…]]` である。その層が、**宣言されておらず**（[B-41](#b-41)）、
**半分しか実装されておらず**（[B-22](#b-22)）、**ほとんど何も報告しない**（[B-39](#b-39) / [B-36](#b-36)）。
4件は別々の不具合ではなく、同じ1つの層の3つの面である。

**着手の順は重要度の順ではない。** 先にやるのは報告の2件（[B-39](#b-39) → [B-36](#b-36)）で、
どちらも lint と終了コードに1つずつ足すだけの作業。これを先に入れると
**B-22 が直すべき箇所を機械が列挙してくれる**（B-39 の診断がそのまま進捗メータになる）。
そのあと [B-41](#b-41) で宣言を1段広げ、最後に [B-22](#b-22) の11プラグインに入る。

> 報告の3件目だった [B-38](#b-38)（明示 ID の衝突）は畳んだ。**着手して分かったのは、
> B-39 の「宣言は既にあるので安い」が成立しないこと** — `inline.effective-in` の
> `section-heading` / `section-body` は**リポジトリ全体でその宣言行にしか存在せず**、
> 読ませる先が無い。しかも宣言の内容自体が誤っている（Steps は `###` に `body: lines` を
> 宣言しているのにリンクは効かない）。効くかどうかは要素ごとではなく**スロットごと**なので、
> B-39 は「既にある宣言を読む」ではなく**新しい宣言軸を立てる**作業になる。
> 詳しくは [B-39](#b-39) 本文。

<a id="b-22"></a>
### B-22: プラグイン内テキストのリンクが効かない

**背景**: `[[…]]` が効くのは `parseInlineFormatting` を通る箇所、すなわち `###` セクションの
見出し・本文と takeaway だけ。スライドタイトル、タイトルスライド、および11個のプラグインが
`layout.ts` で `text:` に直接書き出す箇所（table のセル、quote の本文、steps のラベル等）では
`[[…]]` が生の文字列として表示される。

**Wiki が主題になったので、これは表示の欠けでは済まない。** `renderer/wiki/link-graph.ts` の
`collectRefs` は `layoutSlide(...).textBoxes` だけを走査するので、プラグインが直接描いたテキストの
参照は**リンクグラフにも入らない**。つまり表示が生文字になるだけでなく、その参照先のスライドに
**バックリンクが立たない**。書いた本人は「繋いだつもり」でいて、サイトのどこにも繋がりが現れない。

表示側とグラフ側は**同時に直す**。片方だけ直すと、リンクは青くなるのに逆引きに出ない
（あるいはその逆）という、より分かりにくい状態になる。

**しかも黙る。** `collectRefs` が見ない以上、その参照は `broken` にも入らない —
未解決リンクの一覧にも CI にも出ない。lint も見ていない。書き手に届く信号は
**表示が生の `[[…]]` になることだけ**で、それはスライドを開いた人にしか分からない
（[B-39](#b-39) がこの穴を、直すまでの間だけ塞ぐ）。

**実装方針**: 各所の `text: X` を `richText: parseInlineFormatting(X)` に置き換える。
1行ずつの機械的な変更だが、PPTX/HTML のレンダ分岐が変わるため
`layout-engine.test.ts` のスナップショットと `snapshot-comparison.test.ts` の確認が要る。
`ShapeBox.text` は `richText` を持たないので、型の拡張が別途必要。

**受け入れ基準**: table のセルと quote の本文に書いた `[[slide-id]]` がリンクになり、
**同じ参照がリンク先のバックリンク欄にも現れる**。

**一部対応済み**: agenda は対応した（目次スライドで `[[…]]` が生のまま出ると
索引としてまったく機能しないため）。残りは table / quote / steps / icon-layout /
numbered-list / pattern-language / customer-journey / text-only / lean-canvas。

> この制限は `SKILL.md` と `ontology.yaml`（2箇所）が現時点の仕様として明記している。
> 直したらその3箇所も畳む。

<a id="b-41"></a>
### B-41: サイトの階層が宣言に無い

**背景**: `ontology.yaml` のトップレベルは
`version` / `elements` / `annotations` / `layouts` / `vocabularies` / `field-sets` / `inline` / `limits` の8つで、
**すべて「1つの md ファイルの中」の構造である。** サイトの階層 — デッキの集合、デッキ名、
`order.yaml`、ID がデッキ内で一意であること、`[[deck/slide]]` という参照の形、4段階の解決順 —
は**1つも宣言されていない**。

改名前はそれで筋が通っていた（正本は「md の構造」で、Wiki は `--wiki` という出し方の1つだった）。
**主題が Wiki に移ったので、宣言の輪郭が主題より1段小さいままになっている。**

具体的に困るのは、この道具が「Claude がドキュメントを読んで機械的に使う」ことを前提に
作られている点である。`ontology.md` の記法表には `[[slide-id]]` と `[[slide-id|表示]]` しか無い。
**`[[deck/slide]]` は正本のどこにも書かれていない** — 実在するのは3つの手書きだけ:

1. `link-graph.ts` の `resolveRef` の doc コメント（実装なので正しい）
2. SKILL.md の「リンクの解決順は、① `deck/slide` の明示 → …」（手書き・生成領域の外）
3. 公開サイトの `guide/解決順` スライド（手書き・NumberedList の4項目）

3つが同じ規則を別々に述べていて、どれも互いを照合していない。**規則を変えたら3箇所を
手で直すことになり、直し忘れは検出されない。** これは [B-01](#b-01) が md の構造について
潰した状態そのものが、サイトの層でまだ残っている、ということである。

同じ理由で、[B-39](#b-39) と [B-40](#b-40) はどちらも
「宣言が無いので検査を立てる足場が無い」形をしている。個別に直すこともできるが、
**宣言を1段広げるほうが、その2つが同じ場所から出てくる。**

> このリストには [B-38](#b-38) も入っていたが、**宣言を広げずに畳めた。** 分け目は
> 「デッキをまたぐか」である — ID の一意性はデッキ内で閉じるので `lint.ts` が
> 既に立っているトークン層でそのまま見えた。ここに残る2件は、効く場所（レイアウトを
> またぐ）と deck slug（デッキをまたぐ）で、どちらも足場が無い。

**実装方針**: `ontology.yaml` に `site:` を足す（デッキ集合・`order.yaml`・deck-slug の作り方・
ID の一意性の範囲・参照の形と解決順）。`CONSUMED_KEYS` に足して `gen-ontology-doc.ts` に
`ontology.md` へ出させ、SKILL.md の手書きの解決順はその生成領域に置き換える。
`guide/解決順` は**公開サイトの本文**なので生成物にはできない —
`ontology.test.ts` が宣言の段数とデッキの節数を照合してドリフトを赤くする
（pattern-language の節名で既に採っている手）。

**受け入れ基準**: `ontology.md` を読んだだけで `[[deck/slide]]` が書けて、解決順が分かる。
解決の段を1つ増やすと SKILL.md の生成領域が更新され、`guide` デッキとの食い違いでテストが赤くなる。

<a id="b-39"></a>
### B-39: 効かない場所に書いたリンクを誰も報告しない

**背景**: `ontology.yaml` の `inline` は `effective-in: [section-heading, section-body, takeaway]` と
**書く場所まで宣言している**。そして [B-28](#b-28) が挙げたとおり、`inline` は**誰も読まない宣言**である。
この2つが重なった結果、[B-22](#b-22) の範囲に書かれた `[[…]]` は**4つの経路すべてで見えない**:

| 経路 | 結果 |
|---|---|
| 表示 | 生の `[[seed]]` がセルに出る |
| リンクグラフ | `collectRefs` が見ないのでバックリンクが立たない |
| 未解決リンク | `broken` にも入らない（＝サイドバーにもCIにも出ない） |
| lint | ✅ 「宣言に沿っている」 |

実測（table のセルに `[[seed]]` を1本置いたデッキ）: `--lint --strict` 緑、`--wiki` は
`backlinks: {}` / `resolve: {}` を吐き、HTML には `[[seed]]` がそのまま残る。
**書いた本人に届く信号がゼロである。**

**この穴を通り抜けた実例が [B-44](#b-44)。** 配布デッキに1本、太字の中に書いたせいで死んだリンクが
あったが、どの検査にも出ず、見つかったのは「書いた数と届いた数を突き合わせる」という
**この項目とは別の物差しを、たまたま1回だけ当てたから**だった。原因（1パス設計）は直したが、
**同じ穴に落ちる書き方は他にもある**（B-22 の範囲がまるごとそれである）。
恒常的に赤くする仕組みが要るのはそのため。

[B-22](#b-22) を直せばこの入力は正しく動くようになるが、B-22 は11プラグイン × レンダラ分岐の
作業で、着手までの間ずっとこの穴が開いている。恒常的に赤くする仕組みが要る。

**以前の版は「宣言は既にあるので、検査を足すのは安い」と書いていた。2026-08-10 の実測で
それが誤りだと分かった。** 2点ある。

1. **宣言の語がどこにも繋がっていない。** `section-heading` と `section-body` は、
   リポジトリ全体を grep して **`ontology.yaml` の `effective-in` のその行にしか存在しない**。
   `elements` が持っているのは `section` と `body`、Quote は `leading-body` という第3の語。
   読ませる先が無い3つの文字列である（[B-28](#b-28) の「誰も読まない宣言」の中でも、
   これは**読もうとしても読めない**という一段悪い形）
2. **宣言の内容が誤っている。** Steps は `slots: [{marker: "###", body: lines}]` を宣言していて
   `effective-in: section-body` に素直に当てはまるが、リンクは効かない（実測: steps / quote の
   本文に置いた `[[…]]` は生の文字で出て backlink も立たない）。さらに `agenda/layout.ts` は
   `###` 項目を `richText` で描く一方**スライドタイトルと副題は `text:`** で、
   同じレイアウトの中でも効く場所と効かない場所が混ざる。
   **効くかどうかは要素ごとではなくスロットごと**である

したがって、この項目は「既にある宣言を読む」ではなく**新しい宣言軸を1本立てる**作業になる
（17レイアウト × スロット、+ selfcheck で嘘を防ぐ）。[B-41](#b-41) と同じ種類・同じ規模で、
「lint 1本で塞げる」という P0 昇格の根拠は成り立たない。

**実装方針は2案ある。**

- **(a) 宣言軸を足す**: 各 slot に「インラインが効くか」の印を持たせ、lint が読む。
  B-22 を直すたびに印を裏返す（診断が進捗メータになる）。宣言が正本という筋は通るが、
  **人間が17レイアウトぶん列挙するので漏れうる**
- **(b) 書いた数と届いた数を突き合わせる**（推奨）: [B-44](#b-44) を見つけた物差しの常設化。
  ソースの `[[…]]` と `collectRefs` が集めた参照を突き合わせ、差を「死んだ参照」として
  行番号つきで出す。**宣言が1行も要らず、列挙の漏れが原理的に無い** —
  B-22 の範囲も B-44 の装飾も、まだ知られていない第3の穴も同じ1つの検査で出る。
  [B-36](#b-36) と同じ「ビルド段で分かることを CLI まで運ぶ」配線に乗るので、
  報告経路は1本で済む

**(b) の引き換え**: リンクの解決は lint の2段下流なので `--lint` 単独では出せず、
`--wiki` の検査になる（CI が回るのはそちらなので、守りたい場所は守れる）。
また `guide.md` は `` `[[種ノート]]` `` と**コード表記の中に見本を置いている**ので、
数える前にインラインコードを剥がさないとこの2本が恒久的な誤検出になる
（冒頭の実測表の「235 / 237」の差がまさにこれ）。

**受け入れ基準**: table のセルに書いた `[[…]]` が行番号つきで報告される。
`###` 本文に書いたものは報告されない。B-22 で対応済みの agenda の `###` も報告されない。
`guide` の記法見本は報告されない。

<a id="b-36"></a>
### B-36: 折れたリンクがビルドを止めない

**背景**: `buildLinkGraph` は解決できなかった参照を `broken`（`not-found` / `ambiguous`）に集め、
`template.ts` がサイドバーの `<details>`「未解決リンク N 件」に並べる。**それだけである。**
CLI は何も言わず exit 0 で終わる（実測: 存在しない `[[…]]` を含むデッキで exit 0・標準エラー空）。

**CI だけは止まる。ただし止め方が生成物の日本語の grep である。** `pages.yml` の
「Fail if the wiki has unresolved links」は `grep -q "未解決リンク" _site/index.html` で判定する。
`template.ts` の `<summary>` の文言を変えた瞬間に grep が空振りし、**空振りは「0件」と同じ
exit 0 になる**ので、ガードが外れたことに誰も気づけない。検査が守っている当の対象
（`renderer/wiki/template.ts`）を編集すると検査自身が黙って消える構造で、
これは検査として成り立っていない。折れたリンクを載せた Wiki が公開される経路は、
ローカルでは常に、CI では文言を触った瞬間から開いている。

`--lint --strict` はこれを拾えない。lint はディレクトリを丸ごと受け取れる（実際 8 デッキを
一度に検査している）ので、範囲の問題ではない。**層の問題である** — `lint.ts` が見ているのは
トークン層（「消えたブロックは AST に痕跡を残さない」から）だが、`collectRefs` が読む
`InlineTextRun.link` は**レイアウト段で初めて載る**。リンクの解決は lint が立っている場所の
2段下流にある。したがって折れを検出できるのは `--wiki` のビルド時だけで、その唯一の場所が
黙っている。

（`resolveRef` の3段目が「サイト全体でちょうど1つ」を条件にしていることも効く —
デッキが1つ増えただけで、いままで解決していた参照が `ambiguous` に変わりうる。
デッキ単位で1回検査して済ませられる性質のものではない。）

現時点の `doc/wiki`（7デッキ・79枚）は 0 件。**いま緑なので、赤くする仕組みを入れるなら今が安い。**

**実装方針**: `--wiki` に `--strict` を効かせ、`broken` が1件でもあれば
一覧を標準エラーに出して非ゼロ終了する。既定は現状どおり警告（外部の md をそのまま
流し込む使い方を殺さないため）。CI の publish は `--strict` を付け、**grep のステップは消す**
（残すと「二重に守っている」ように読めるが、実際に守るのは exit code のほうだけになる）。

**受け入れ基準**: 存在しない `[[…]]` を1つ足すと `--wiki --strict` が非ゼロで落ち、
`fromId → [[ref]] (reason)` が読める形で出る。曖昧（複数一致）も同じ扱いで落ちる。
`pages.yml` に生成物の文言を読むステップが残っていない。

> **`broken` に入らない折れ方がある。** [B-22](#b-22) の範囲（プラグインが直接描くテキスト）に
> 書いた `[[…]]` は `collectRefs` が見ないので、リンクにならないだけでなく
> **未解決リンクとしても数えられない**。この項目を入れても、そこは緑のままである
> （見えるようにするのは [B-39](#b-39)）。

## P1 — 読めない・書けない・気づけない

読み手がサイトから何も引けない（[B-37](#b-37) / [B-42](#b-42)）、書き手が宣言どおりに書けない
（[B-26](#b-26) / [B-27](#b-27) / [B-40](#b-40)）、そしてどちらの側も間違いに気づけない
（[B-32](#b-32) / [B-07](#b-07)）。P0 と違って一本の層ではないが、
**どれも「主題を実際に読み書きする人が踏む」ところにある。**

<a id="b-37"></a>
### B-37: 絞り込みが本文を見ていない

**背景**: サイドバーの絞り込みが照合する `data-search` は
`` `${entry.title} ${entry.globalId}`.toLowerCase() ``（`renderer/wiki/template.ts:21`）、
つまり**スライドの題と ID だけ**。本文・節見出し・takeaway は入っていない。

Wiki は「読み終えたところから、また入り直す」ための道具で、入り直す手がかりは
たいてい本文の中の語である。題を覚えていないと辿り着けないのは、索引としての取りこぼしが大きい。
現時点で7デッキ・79枚あり、目次を上から眺めて探すのは既に実用的でない。

**ブラウザの検索も効かない。** `.wiki-slide { display: none }`（`styles.ts:205`）なので、
`Ctrl+F` が見ているのは**いま表示している1枚だけ**である。つまりこのサイトには
**本文を引く手段が1つも無い** — 絞り込みは題と ID しか見ず、ブラウザの検索は78枚を見ない。
「本文も見る絞り込み」は便利さの追加ではなく、唯一の全文検索を用意する話になる。

**実装方針**: `data-search` に本文のプレーンテキストを足す。
`layoutSlide(...).textBoxes` からテキストを集める経路は
`link-graph.ts` の `collectRefs` と同じなので、走査を1本にまとめて両方に使う。
サイトが自己完結（外部リソース禁止）なので、索引は HTML に埋め込む。
分量が問題になるなら、まず「節見出し + takeaway まで」の中間案がある。

**受け入れ基準**: 本文にしか現れない語で、そのスライドが絞り込みに残る。
生成 HTML のサイズが実用の範囲に収まる（`wiki.test.ts` の自己完結性テストは引き続き通る）。

<a id="b-42"></a>
### B-42: 孤立したスライドを誰も数えない

**背景**: `buildLinkGraph` は `forward`（どこへ出ているか）と `backlinks`（どこから来ているか）の
両方を作る。`backlinks` はビューアに渡って「このスライドへのリンク」欄になる。
**`forward` は `WikiSite` に載るだけで、どこからも読まれない**（利用者は `wiki.test.ts` だけ）。

被リンクゼロのスライド — 目次から選ぶ以外に辿り着けないスライド — は、
その `backlinks` に鍵が無いことで**既に分かる状態にある**のに、数える場所が無い。実測:

| 内訳 | 件数 |
|---|---|
| 全スライド | 79 |
| 被リンクゼロ | 11 |
| ├ デッキの表紙 | 6（構造上そうなる。除外してよい） |
| ├ `index` の表紙 | 1（同上） |
| └ `guide` の本文 | **4**（`書き方` / `解決順` / `操作` / `使いどころ`） |

`guide` の4枚は本当に孤立している。**機能ガイドという、いちばん最初に読ませたいデッキが、
サイトの中では誰からも指されていない。** 手で作った `index.md` が全スライドを網羅しているか
確かめる手段が無いので、デッキを足すたびに同じことが起きる（`patterns-meta` は
索引に入っているが、それは書いた人が覚えていたからである）。

このサイトが載せているパターンのほうが先に言っている — `けもの道` は「踏まれた道を索引にする」、
`剪定` は「繋がっていないものを見つけて畳む」。**道具が自分の載せている物差しを自分に当てていない。**

**実装方針**: `--wiki` の出力に「被リンクゼロ N 枚」を出す（既定は情報、`--strict` でも
落とさない — 孤立は誤りではなく手入れの合図なので、[B-36](#b-36) の折れリンクとは扱いを分ける）。
表紙（`deckIndex === 0` の TitleSlide）は数えない。サイドバーにも `<details>` で
未解決リンクの隣に並べると、手入れの入口が1箇所に揃う。
`forward` はここで初めて使い道が出る（「出るリンクがゼロ」＝行き止まりも同じ欄で出せる）。

**受け入れ基準**: `--wiki` が孤立したスライドの一覧を出す。表紙は含まない。
`guide` の4枚が消える（＝索引から指す）まで一覧に出続ける。

<a id="b-26"></a>
### B-26: 文字数の数え方が宣言に反する

**背景**: `ontology.yaml` の `limits.counts` は
「本文と見出し（Markdown 構文を除く）。**リンクは表示ラベルだけを数え、URL は数えない**」と宣言する。
正本の `countPlainTextChars`（`schema/validation.ts`）はそのとおり `stripInlineFormatting` を
通し、リスト記号も落とす。

ところが同名の関数が**6つのプラグインの `index.ts` にコピーされている**
（agenda / icon-layout / lean-canvas / numbered-list / steps / wiki-pattern）。
いずれも `stripInlineFormatting` もリスト記号除去も持たない弱い版で、`#`・`<!--…-->`・
空行しか落とさない。結果、**URL とリスト記号がそのまま文字数に入る**。
2026-08-08 の調査時点では5つだった — **新しいプラグインが増えるたびに写しが増えている。**

再現（同一の本文、リンク1本、URL は 1200 文字強）:

| 入力 | 結果 |
|---|---|
| `### 見出し` + `[ラベル](長いURL)`（Default） | ✅ 生成成功 |
| `<!--lean-canvas-->` + `### 課題` + 同じ本文 | ❌ `ValidationError` `charCount: 1230` |

宣言では両者とも「ラベル3文字」のはずで、レイアウトを変えただけで通らなくなるのは
オントロジーが約束していない挙動。**Wiki のデッキはリンクを多く張るので、この差は日常的に踏む。**

**実装方針**: `registry.getCharCounter` がプラグインから受け取るのは「どのフィールドを数えるか」
だけにして、正規化は `validation.ts` の `countPlainTextChars` 1本に寄せる。
プラグイン側のコピーを削除する。

**受け入れ基準**: 同じ本文は、レイアウトの `max-chars` が同じなら同じ文字数になる。
上の URL ケースを回帰テストにする。

<a id="b-27"></a>
### B-27: lint の盲点（タイトルスライド・`slot.body`）

**背景**: lint がトークン層を見ているのは「消えたブロックは AST に痕跡を残さない」から
（`lint.ts` 冒頭）。その設計意図に対して、**黙って消える2つの経路が検査されていない**。

1. **タイトルスライドを一切検査しない**。`detectLayout` は `##` を持たないトークン列に
   `undefined` を返し、`lintTokens` はそこで `continue` する。実測: タイトルスライドに書いた
   `### 未宣言の見出し` + 本文は出力から消えるが `--lint --strict` は「✅ 宣言に沿っている」を返す。
   宣言側は `annotations[].applies-to` に骨格要素を持っているのに、lint は `layouts[].annotations` しか
   参照していないので、この情報が使われていない
2. **`slots[].body` の `free｜lines｜bullets-only｜none` が未強制**。
   `gen-ontology-doc.ts` が文書に印字するだけで、誰も照合しない。
   実測: カスタマージャーニーの `#### タッチ` 直下に非箇条書きの行を書くと
   `customer-journey/handler.ts` の `if (!token.text.startsWith('-')) return` で捨てられ、
   HTML にも PPTX にも現れないが `--lint --strict` は緑

**実装方針**: (1) `detectLayout` が undefined を返す断片にも、TitleSlide 用の宣言
（`elements.title-slide`）を当てて注釈スコープと未宣言 `###` を見る。
(2) `slot.body` を lint の検査項目に加える（`bullets-only` の slot 配下で `- ` 以外の
BodyText を warning）。

**受け入れ基準**: 上の2ケースが `--lint` で警告になる。既存デッキが引き続き
`--lint --strict` を通る（通らないものが出たらデッキ側の実バグ）。

<a id="b-40"></a>
### B-40: デッキ名が2つの語彙を持つ

**背景**: 「ファイル名がデッキの slug であり `[[deck/slide]]` のリンク先でもある」は
`order.yaml` の冒頭・`deck-order.ts` の doc コメント・SKILL.md・CLAUDE.md が揃って書いている
**この道具の中心的な約束**である。実装はそうなっていない。

- `order.yaml` の照合は `deckName(file)` = **拡張子を落としただけの生のファイル名**（`deck-order.ts:22`）
- リンク先になる slug は `slugify(source.name)`（`pipeline.ts:179`）= **NFKC 正規化 + 小文字化 +
  `_`/空白をハイフンに + 記号落とし**

つまり `My_Deck.md` は、`order.yaml` には `My_Deck` と書き、`[[my-deck/…]]` と指すことになる。
**同じものを指す2つの綴りが、どちらのドキュメントにも書かれていない。**

さらに**衝突が黙る**。実測（`My_Deck.md` と `my-deck.md` を同じディレクトリに置く）:

```
"id":"my-deck/a"      ← My_Deck.md
"id":"my-deck-2/b"    ← my-deck.md
```

`buildSiteIndex` の `unique()` がデッキ slug にも連番を足すので、2つ目のデッキは
**`my-deck-2` という、どのファイル名にも `order.yaml` にも現れない名前**でしか指せなくなる。
exit 0、警告なし。[B-38](#b-38) と同じ壊れ方（黙って一意化して、動いているように見せる）が
**スライドの層では直ったのに、デッキの層でまだ起きている。**

**実装方針**: slug を導出する場所を1つにし（`slugify` を通すか通さないかを決める）、
`orderDeckFiles` の照合をその slug に揃える。デッキ slug の衝突は連番にせず誤りとして止める
（スライド ID と違い、デッキはファイルなので書き手が改名できる）。
ファイル名と slug が食い違う場合に何と書けばよいかを、SKILL.md の該当箇所に1行で書く。

**受け入れ基準**: `order.yaml` に書く名前とリンクに書く名前が一致する。
slug が衝突する2つの md を置くと `--wiki` が非ゼロで落ち、両方のファイル名を挙げる。

<a id="b-32"></a>
### B-32: 存在しない保証を主張しているコメント・数え上げ

**背景**: 「乖離しうる事実の置き場を1つにした」あとも、**保証の所在についての記述**が
乖離している。これは普通のドキュメント誤りより悪い — 読んだ人が「守られている」と信じて
チェックを足さなくなる。

**予言していた失敗が実際に起きた。** `selfcheck` は `レイアウト 17 / プラグイン 12` と言うのに、
`SKILL.md:24` と `CLAUDE.md:14` の「**16レイアウト**」は生成領域の外の手書きのままで、
17個目（wiki-pattern）が入った時点で黙って嘘になった。`docs-consistency.test.ts` が
見ているのは `11ディレクトリ` / `12プラグイン登録` だけで、この2文は無防備。
CLAUDE.md 自身が「そちらにある内容をここへ写さない（写した瞬間、四重管理とドリフトが始まる）」と
書いている、その直後の行で写している。

**同じ失敗がもう1件、Wiki の説明の中で起きている。** `SKILL.md:160` は配布サンプルを
「機能ガイド + パターンの2主題 × 2デッキ + 索引の**6デッキ**」と書くが、`doc/wiki/` には
**7つ**の md がある（`patterns-meta` を足したときに更新されなかった）。`docs-consistency.test.ts` は
プラグイン数・テストファイル・レイアウト件数を照合するが、デッキ数は見ていない。
`order.yaml` が正本になりうるので、突き合わせ先はある。

他:

- `plugins/lean-canvas/layout.ts` の `findCellIndex` のコメントが
  「その `key` は上の `LEAN_CANVAS_CELLS` の `name` と対応する（**selfcheck が両者を突き合わせる**）」
  と書くが、**`selfcheck.ts` は lean-canvas を import していない**。実際に守っているのは
  `ontology.test.ts` の描画テスト。書き換えるべきは保証の名前
- `renderer/wiki/link-graph.ts` の `collectRefs` のコメントが
  「1スライドにつき `layoutSlide` が2回走る（グラフ用と描画用）」と書くが、
  実際は **3回**（`buildLinkGraph` / `buildResolutionTable` / 描画）。
  数え間違いそのものは無害だが、「許容する」判断の根拠が実測とずれている

**実装方針**: コメントを実際のガード（`ontology.test.ts`）の名前に直すか、selfcheck に
本当に照合を足す（[B-29](#b-29) のコアレイアウト照合と同じ作業になる）。
レイアウト件数は `gen-ontology-doc.ts` の生成領域に入れるか、`docs-consistency.test.ts` で
宣言の件数と突き合わせる。

**受け入れ基準**: コードコメントが主張する保証が全て実在する。レイアウト件数を1つ増やすと
テストが赤くなる。デッキを1つ足しても同じく赤くなる。

<a id="b-07"></a>
### B-07: 固定要素数レイアウトの柔軟化

**背景**: IconColumn / IconCard は TypeScript の tuple 型で **3要素固定**（2個や4個は型エラー）。
CustomerJourney も4行固定。**4件以上書くと4件目以降が黙って捨てられ、2件以下だと黙って Default に
落ちる** — どちらも警告が出ない。Claude が生成するコンテンツは必ずしも3項目に収まらず、
機械的生成の入力制約として厳しすぎる。

**実装方針**: tuple を長さ2〜4の配列 + バリデーションに変更し、レイアウト側
（`plugins/icon-layout/layout.ts` 等）で要素数に応じた幅・フォントサイズ計算を行う
（Grid の `calculateGridSpacing` と同様の段階縮小）。可変化しないなら、
せめて**捨てるときに lint が言う**のが最低線。

**受け入れ基準**: `<!--icon-cols-->` で2〜4項目が均等配置される。3項目の既存スナップショット
テストが変化しない（後方互換）。

> `ontology.yaml` がこの制限を現時点の仕様として明記している。直したらそこも直す。

<a id="b-28"></a>
### B-28: 宣言の「誰が読むか」が宣言に無い

**背景**: `ontology.yaml` は自らを正本と宣言し、CLAUDE.md も「コードに語彙や数値を再定義しない」と
書いている。だが実際に実装を駆動しているのは4つだけ:

1. プラグインのディレクティブ認識（`registry.ts` が `directiveForPlugin` から導出）
2. 文字数上限（`validation.ts` の `maxCharsForTag` / `isCharCountExcluded`）
3. `lean-canvas-blocks` と `journey-rows` の語彙（`resolveTerm` 経由）
4. lint（`lint.ts` が layouts / vocabularies / field-sets / cardinality を読む）

**宣言のみで誰も読まないもの**: `elements` 全体、`annotations[].pattern｜applies-to｜cardinality｜position｜example`、
`layouts[].directives[].pattern` と `kind: code-fence`、`slots[].body`、
`field-sets[].keys[].kind｜separator`、`inline`（`counts-chars` を含む）、
`vocabularies.pattern-sections`。

どれが規範でどれが解説かが宣言自身に書かれていないので、読み手（Claude を含む）は全部を
規範として読む。[B-26](#b-26) / [B-27](#b-27) はどちらもこの構造から出た具体例。

さらに `selfcheck` の `CONSUMED_KEYS` は**トップレベル名しか見ていない**。
「黙って文書化されない宣言は出してはいけない」という当のコメントを持ちながら、
サブキーの未消費は緑のまま通る — 仕組みが防ごうとした失敗が、一段下で起きている。

**実装方針**: 各フィールドに `enforced-by:` 相当の印を持たせるか、`selfcheck` に
「宣言されているが誰も読まないフィールド」の一覧をサブキーまで降りて出させる。
前者は宣言が重くなるので、まず後者（可視化）から。

**受け入れ基準**: `selfcheck` の出力から、宣言の各項目が「実装を駆動する / 文書のみ」の
どちらかに分類できる。新しいサブキーを足して誰も読まなければ、その一覧に載る。

<a id="b-29"></a>
### B-29: コア側の宣言駆動化

**背景**: プラグイン側は宣言駆動になったが、コア側は手書きのままで、
しかも selfcheck がコアを見ていない。

- **コアディレクティブの正規表現が二重管理**。`parser/tokenizer.ts` の
  `matchLeftDirective`〜`matchTakeawayMarker`（8本）と `ontology.yaml` の `pattern:` が
  同じものを別々に持つ。`selfcheck.ts` はパターンが**コンパイルできるか**しか見ていないので、
  どちらかを変えても赤くならない
- **selfcheck がコアレイアウトを飛ばす**。`if (!layout.plugin) continue` により、
  `Default` / `LeftRight` / `TopBottom` / `Grid` / `CodeDisplay` の5つと、`produces` 側の
  `PatternLanguageDetail` は、**実クラスの `_tag` と一度も照合されていない**。
  「宣言 ⇔ 実装を両方向で突き合わせる」と謳っているのはプラグインの12個だけ
- **レイアウト優先順位が4箇所**。正は `parser/slide-converter.ts`、写しが
  `lint.ts` の `CORE_PRECEDENCE`、`renderer/layout/index.ts` のディスパッチ、
  `schema/validation.ts` の文字数分岐。宣言側に `directives[].pattern` と
  `kind: code-fence` があるので、行を宣言のパターンに当てれば表ごと消せる
  （`pluginId.split(":")[0]` も一緒に消える）
- **`numbered-list` の `bar` 綴りにテストが無い**。`ontology.test.ts` は
  `directives[0]`（= `circle`）だけをトークン化する。`index.ts` の
  `circle|bar` 正規表現から `bar` を落としても緑のまま
- **pattern-language の語彙が handler にリテラルで散っている**。節名は約10箇所、
  `sub-labels` の照合も handler が自前で持つ。600行の状態機械の改修になるため繰り延べた。
  当面は `ontology.test.ts` が「宣言した節名がハンドラのソースに存在すること」を照合して
  ドリフトを赤くする（内容の一致までは見ていない）
- **ビルダーへの診断チャネルが無い**。lint がトークン列に対する2つ目のパーサになっている。
  ビルダーが「いま落とした」と報告できれば、入れ子モデルの写しが要らなくなる

**受け入れ基準**: コアディレクティブが宣言のパターンから導出される（または両者の一致がテストで
留まる）。selfcheck がコアレイアウトの `name` と `produces` を実クラスの `_tag` と照合する。

<a id="b-30"></a>
### B-30: 層ごとに名前が違う同一概念

**背景**: `ontology.yaml` は冒頭に用語体系（`element` / `annotation` / `layout` / `slot` /
`vocabulary` / `field-set` / `inline`）を置いているが、実装の識別子には効いていない。

- **同じものが4つの名前を持つ**: 宣言の `Slot` → parser の `RawSection`
  （`parser/builder-types.ts`）→ schema の `TextBlock`（`schema/presentation.ts`）→
  layout の `TextBox`（`renderer/layout/types.ts`）。変換点は `parser/slide-converter.ts` の
  `toTextBlocks`
- **`element` が2つの意味を持つ**: 宣言では骨格要素（`#` / `##` / `###`）、
  `renderer/html/element-renderers.ts` ではレンダラのボックス
- **`layout` が5つの意味を持つ**: `SlideLayout`（検証済みデータ）/ `LayoutMode`（パーサの状態）/
  各プラグインの `layout.ts`（座標計算）/ `LayoutResult`（幾何）/ 宣言の `Layout`（宣言レコード）

オントロジーの目的が「同じものを同じ名前で呼ぶ」ことなら、宣言の語彙が実装の識別子に届いて
いないのは中心的な未達。

**実装方針**: まず宣言側に「宣言の語 ⇔ 各層の型名」の対応表を持たせ、`gen-ontology-doc.ts` に
出させる（読む側の混乱がまず消える）。改名は影響が広いので段階的に、`element` の衝突など
実害の大きいものから。

**受け入れ基準**: `ontology.md` に層をまたぐ対応表がある。少なくとも `element` の二義が解消する。

<a id="b-31"></a>
### B-31: `LayoutPlugin` に足りないモデル

**背景**: プラグイン機構が表現できない事情が、特例フォールバックとハックとして散っている。

- **1プラグイン = 1タグの前提**。`pattern-language` は `PatternLanguageOverview` と
  `PatternLanguageDetail` の2タグを出すのに `layoutTag` は1つしか持てず、
  `registry.ts` の `getCharCounter` と `ontology/index.ts` の `getLayoutByTag` に
  `produces` 経由の特例フォールバックが2本ある（後者のコメントに、これが無かったとき
  Detail に 1024 ではなく 1000 が適用されていたと記録されている）。
  `LayoutPlugin` に `producesTags` を持たせれば両方消える
- **`titleFontSize: 1` が「タイトルを描かない」の代用**。`agenda/index.ts` と
  `pattern-language/index.ts` が 1pt フォントで隠している。`showTitle: false` としてモデル化すべき
- **ファイル構成が守られていない**。`customer-journey` と `text-only` は `constants.ts` を持たず、
  `customer-journey/layout.ts` は `PRIMARY_COLOR = "0891B2"` をハードコードしている。
  この色は `schema/theme.ts` の `iconCardAccentColors` にもある同じ値で、テーマを変えても追随しない
  （[B-12](#b-12) と重なる）

**受け入れ基準**: `registry.ts` と `ontology/index.ts` から `produces` の特例分岐が消える。
`titleFontSize: 1` が無くなる。

<a id="b-23"></a>
### B-23: 記法そのものの整理

**背景**: `ontology.yaml` に md の構造を書き起こしたことで、「宣言はできるが素直ではない」箇所が
輪郭を持った。記法を変えない方針で宣言と検証だけを入れたので、以下は未着手のまま残る。
どれも既存デッキの書き換えを伴うため、まとめて1回で行うか、やらないかを決める必要がある。

- **デッキ frontmatter が無い**: 先頭の `---` がスライド区切りとして読まれるため、デッキ名・既定テーマ・
  サイトタイトルを md 自身に書けない（`--site-title` は CLI 引数でしか渡せない）。導入するなら
  「先頭の `---` は、直後が `key: value` なら frontmatter」という例外規則が要る
- **暗黙の位置依存**: Steps の本文は「1行目が役割名」、Quote の `###` は著者、Agenda のディレクティブ
  直後の行は副題。宣言で説明はできるが、`####` の名前付きラベルにするほうが読んで分かる
- **固定件数**: IconColumns / IconCards は3件ちょうど（[B-07](#b-07) と重なる）
- **日本語ディレクティブ**: `<!--カスタマージャーニー:-->` だけが日本語で、末尾のコロンにも意味が無い。
  英語 `<!--customer-journey-->` に寄せるなら旧綴りの受理期間が要る
- **語彙の日英混在**: lean-canvas は `課題` と `problem` の両方を受理するが、pattern-language の節名は
  日本語のみ。受理の広さが語彙ごとに違う

**受け入れ基準**: 変えるものを選び、`ontology.yaml` の宣言・`doc/` のデッキ・
`__tests__/markdown-spec/` の入力を同時に更新して、`--lint --strict` が通る。

<a id="b-43"></a>
### B-43: 1枚 HTML の伸び方に上限が無い

**背景**: サイトは全スライドの DOM を最初から1枚の HTML に持つ。これは設計上の選択で、
見返りがはっきりしている — ホバープレビューが `cloneNode` だけで作れ（表示とプレビューが
食い違いようがない）、外部リソースが1つも要らない。**代わりに、サイズがスライド数に比例する。**
実測（7デッキ・79枚）:

| 内訳 | 大きさ |
|---|---|
| 合計 | 820 KB |
| スライドの DOM | 590 KB（1枚あたり約 7.5 KB） |
| 図解 SVG（インライン展開・42本） | 148 KB |
| CSS | 13 KB |
| ブートストラップ JSON | 20 KB |

1枚あたり約 10 KB。**育つことが前提の道具なので、300枚で約 3 MB、1000枚で約 10 MB になる。**
そのすべてを、1枚目を表示する前にダウンロードして構文解析する。
[B-37](#b-37) は本文の索引をここへ足す話なので、**この見積りの上に乗る**
（B-37 が「実用の範囲に収まる」を受け入れ基準に挙げているのは、収まる範囲がどこかを
誰も測っていないからである。上の表がその起点になる）。

**いま困ってはいない。** 820 KB は許容範囲で、生成は 2.1 秒。項目として持つのは、
**どこで困るかを決めていない**ことのほうが問題だから — 気づくのは「重い」と言われたときになる。

**実装方針**: まず物差しを置く（`wiki.test.ts` に「1枚あたりのバイト数」の上限を1つ）。
超えたら考える、の状態にする。手当ての候補は、効きの大きい順に:
(1) 図解 SVG の重複排除 — 同じ図を指す参照が複数あれば1本にする、
(2) インラインスタイルの共通部分を CSS クラスへ（`--html` と同じ DOM を出す約束と衝突するので
両方に効かせる必要がある）、
(3) デッキ単位でファイルを割る（**ホバープレビューと自己完結性を失う** — 見返りを捨てる手なので最後）。

**受け入れ基準**: 1枚あたりのバイト数にテストの上限がある。その上限の根拠が
（実測とともに）書かれている。

<a id="b-35"></a>
### B-35: 読まないコードフェンスをコアで吸収する

**背景**: コアの `handleCodeFenceOpen`（`parser/handlers/inline.ts`）はモードを問わず走り、
`mode` を `"code"` にする。そのためプラグインのブロックの中に無関係なコードフェンスが1つ
あるだけで、セクションのルート先が消えてスライドが CodeDisplay として変換される。
wiki-pattern はこれを自前の `handleCodeFenceInWikiPattern` で飲んで回避しているが、
同じことは steps / agenda / table / quote / icon-cards などフェンス枠を宣言していない
全レイアウトで起きる。**気づいたプラグインだけが自衛している**状態。

**実装方針**: `handlers/index.ts` の `handleH4Core` と同じ位置に `handleCodeFenceCore` を置き、
いまのモードのレイアウトがフェンス枠を宣言していない（`markerKind(slot.marker).kind !== "code-fence"`）
ならフェンスのトークンを吸収する。`handleCodeFenceInWikiPattern` は削除できる。
併せて lint に「…はコードフェンスを読まない」を足す — `####` と画像には既にある診断で、
フェンスだけが吸収されるのに黙っている。

**受け入れ基準**: フェンス枠を持たないレイアウトのブロックにコードフェンスを置いても
スライドの型が変わらず、lint がその行を「描かれない」と報告する。

<a id="b-04"></a>
### B-04: 任意のレイアウトへの画像挿入

**背景**: 画像を読むのは **WikiPattern の図解スロットだけ**で、対象も SVG のみ
（HTML はインライン展開、PPTX は data URI で `addImage`）。行まるごとの `![alt](src)` は
`Image` トークンとして認識され、パスは `baseDir`（md の置かれたディレクトリ）から解かれ、
読み込みは `assets.ts` の1関数だけが行う。存在しないパスと宣言外の拡張子は行番号つきの
ParseError で落ちる。

**残件は本題のほう** — 任意のレイアウトに画像を置けるようにする `ImageBox` の追加と、
ラスタ画像・アスペクト比保持・領域内フィット。いまは画像を読まないレイアウトに置かれた参照を
lint が「描かれない」と報告するだけで、置く手段が無い。

**実装方針**: レイアウトエンジンに `ImageBox` を追加し PPTX/HTML 両対応。
LeftRight レイアウトとの組み合わせ（左テキスト + 右画像）を最優先ユースケースとする。
**枠のほうを図の縦横比に合わせる**（`svgAspectRatio()` を使う wiki-pattern と同じ方針 —
枠を図と違う比で置くと HTML は余白を作り PPTX は歪ませ、別々に崩れるので気づきにくい）。

**受け入れ基準**: `![説明](./fig.png)` が Default / LeftRight で PPTX/HTML 両方に表示される。
存在しないパスは ParseError で明確に失敗する。

<a id="b-33"></a>
### B-33: 3者比較が見ていない残り

**背景**: [B-24](#b-24) で3脚を揃えたが、意図的に対象外にした範囲と、直さずに
コメントで明示した弱点が残る。「何を保証していないか」を項目として持っておく
（[B-32](#b-32) と同じ理由 — 書いていない除外は「守られている」と読まれる）。

- **幾何のみの図形が比較対象外**。境界ボックス・塗り・コード背景・SVG アイコンは
  `deco:` で除外している。`inventory-diff.ts` の語彙がテキスト前提（`text` /
  `font_name` / `font_size` / `bold` / `color`）なので、幾何だけの脚を足すには
  両インスペクタが「テキストの無い `<p:sp>` / `<p:pic>` / div」を拾えるようにする必要がある。
  名前は既に両生成物に書かれているので、緩めるのはフィルタだけ
- **`slide-builder.ts` は codeBoxes があると borderBoxes を丸ごと描かない**。
  HTML は常に描く。実在する PPTX/HTML の乖離だが `deco:` なので現在の比較には出ない
- **`pptx-inspector.ts` は段落の最初の `<a:rPr>` しか読まない**。同一段落内で書式が
  変わるデッキ（太字の途中挿入など）では2番目以降の run の書式を取りこぼす。
  インベントリ側も「行の先頭 run」で揃えてあるので現状は一致するが、
  両方が同じ弱点を持っているだけで、真に一致を検証しているわけではない
- **Wiki の脚は比較に無い**。サイトのスライド DOM は `html/` の `renderSlide()` を
  再利用するので座標は HTML と同一だが、サイト合成（ID の名前空間化・解決表・バックリンク）は
  `wiki.test.ts` だけが見ている

**受け入れ基準**: 上の各点について、直すか「直さない理由」を持つ。
少なくとも幾何のみの図形が比較に入る。

<a id="b-34"></a>
### B-34: 整理で見送った重複

**背景**: [B-24](#b-24) の差分を再利用・単純化・効率・深さの4観点でレビューし、写経は潰した。
残りは「指摘は正しいが、直すと差分の外が主体になる」もの。まとめて1項目にしておく。

- **改行 → `breakLine` の細工が複数箇所**。`slide-builder.ts` の2箇所は
  `withBreakLines` に寄せたが、`syntax-highlighter.ts` の `codeTextRunsToPptxRuns` は
  独立したまま。違いは末尾の空断片の扱いだけ（`"a\n"` が前者は2断片、後者は1断片）で、
  **段落数が一致しているのは `pptx-inspector` の空段落フィルタが吸収しているから**であり、
  構造的な保証ではない。import 1行で寄せられる状態にはなっている
- **PPTX の `addText` は5箇所あり、2箇所が `withBreakLines` を通らない**
  （絵文字アイコンとシェイプのテキスト）。いまは改行を含まないので実害は無いが、
  「素の文字列を渡さない」が private 関数の doc コメントでしか表明されていない。
  `renderer/pptx/text-runs.ts` に寄せて、型で迂回できなくするのが深い直し
- **デッキ一覧が3つのテストに独立して書かれている**（`e2e.test.ts`、
  `ontology.test.ts`、`three-way-verify.test.ts`）。
  デッキを足す・除外を変えるたびに3箇所を探すことになる
- **`snapshot-comparison.test.ts` は同じ6手順を18回書き写している**。

<a id="b-45"></a>
### B-45: テストコードが型検査されていない

**背景**: [B-25](#b-25) で `npm run typecheck` が入ったが、見ているのは `src/` だけである
（`tsconfig.json` の `exclude` に `__tests__` がある）。**テストは3000行以上あって、
型検査を一度も受けていない。**

`__tests__` を含める tsconfig を作って測ると **38 件**出る。中身はほぼ1種類で、
`SlideLayout` の判別共用体を絞り込まずにプロパティを読んでいるもの
（`Property 'rows' does not exist on type 'SlideLayout'` など）。`rootDir` も
`./src` なので、テストを含める tsconfig ではそこも変える必要がある。

**急がない理由**: vitest は型を捨てて実行するので、綴りを間違えたプロパティは
`undefined` になり**アサーションが落ちる**。つまり実行時には気づける。
`src/` と違って「黙って間違う」側ではない。

**それでも項目として持つ理由**: **テストはこの道具の検査の土台である。**
土台だけが型検査の外にあると、リファクタで型を変えたときテスト側の追随漏れが
コンパイル時に出ず、38 件の中に紛れる。件数が増えるほど「あとでやる」が難しくなる。

**実装方針**: `tsconfig.test.json`（`rootDir` を `.` にし `__tests__` を include、
`noEmit`）を足し、`npm run typecheck` を両方走らせる。38 件は
`expect(slide._tag).toBe(...)` 相当の絞り込みか、テスト用のヘルパで潰す。

**受け入れ基準**: `__tests__` を含めた型検査が緑。`ci.yml` がそれを走らせる。

**B-25: 型検査が CI にもテストにも無かった** — 直したのは2つで、**大きいのは後者**である。

`(string | undefined)[]` が出て `Theme` に代入できなくなっていた。配列を再帰から外して解決。
意味としてもそれが正しい — パレットの3要素目だけを部分上書きする操作に意味は無く、
穴の空いた配列を許すと描画側が `undefined` を色として受け取る。
`package.json` に `typecheck` を足した（vitest は esbuild で型を捨てるので `npm test` では出ない）。

**CI**: こちらが本体だった。`pages.yml` のトリガは `main` への push と手動だけで、

宣言に照らしたデッキの lint・3者比較・[B-38](#b-38) の `slide-id` — は全部

<a id="b-38"></a>
**B-38: 明示した ID の衝突が黙って別の ID になっていた** — 報告を足すだけの項目として積んだが、
**採番の規則そのものに穴があった**ので両方を直した。

積んだときに書いていたのは「同じ `<!--id:seed-->` を2枚に書くと2枚目が黙って `seed-2` になる」で、
これは実測どおりだった（`--lint --strict` 緑・`--wiki` exit 0・サイトの ID は `dup/seed` と
`dup/seed-2`）。**折れたリンクより悪い**のは、`[[seed]]` が**解決してしまう**ことである — 常に1枚目へ。
2枚目は誰からも指されないスライドとしてサイトに残り、未解決リンクの一覧にも出ない。

**着手して見つかったのは、衝突がもう1種類あることだった。** `unique()` は自動 slug と明示 ID を
区別しないので、**自動 slug が明示 ID に勝つ**:

```markdown
# 設計                    ← 表紙。slugify("設計") が先に `設計` を取る
---
## 設計の考え方
<!--id:設計-->            ← 書き手が明示した。しかし `設計-2` に降格される
```

`[[設計]]` は表紙に着き、バックリンクも表紙に立つ。lint 緑、exit 0。**勝敗が md の並び順で
決まる**ので、無関係なスライドを1枚前に足しただけで既存のリンクの行き先が変わりうる。
`<!--id:-->` は書き手が「この名前で指す」と宣言する唯一の手段なのに、**予約として機能していなかった**。

**もう1つ、`unique()` は重複した ID を出しうる状態だった。** 連番を「その base が何度目か」の
カウンタで決めていたので、`## X-2` が先にある状態で `## X` が2枚続くと、2枚目が `x-2` を
再発行して1枚目と衝突する（サイトのリンクが解決できなくなる）。

直したのは3点:

- **明示 ID を予約として扱う**（`parser/slide-ids.ts`）。変換を先に済ませて明示 ID の集合を
  作り、自動 slug はそこを避けて連番に回る。**`[[…]]` の行き先が md の並び順に依らなくなった**
- **連番は「その綴りが空いているか」で決める**。カウンタをやめたので重複が出ない
- **明示 ID 同士の衝突は lint が報告する**（`ontology/lint.ts` の `slide-id`）。一意化そのものは
  続ける（重複するとリンクが解決できない）。どちらが間違っているかは機械に決められないので、
  両方の行番号を出して書き手に返す。自動 slug が押さえられた側にも「この見出しの ID は
  `設計-2` になる」と伝える

検査をトークン層に置けたのは、**ID の一意性がデッキ内で閉じている**ため（`site-index.ts` が
`deck-slug/` を前置する）。lint は1ファイルずつ呼ばれるので、検査の範囲もそのまま合った。
**サイトの階層の宣言（[B-41](#b-41)）を待つ必要が無かった**のはこの1点による。
取り逃がすのは1ブロックが複数スライドを生む場合の派生 ID（`--2`）の衝突だけで、
何枚生まれるかはトークン層の2段下流でしか分からない。

**既存の ID は1枚も変わっていない**（`doc/wiki` の79枚を採番の前後で突き合わせ、順序込みで一致）。
配布デッキには予約が絡む衝突が1件も無く、`Spec.md` の同名見出し2枚だけが自動 slug の連番
＝正しい振る舞いのケースだった。`slide-id.test.ts` が予約・並び順非依存・重複の不発行を、
`ontology.test.ts` が診断の行番号と「タイトルが同じだけの2枚は報告しない」を留めている。

> `slide-ids.ts` のコメントが主張していた「明示 ID の衝突も黙って解決せず、あとで /lint 相当の
> 検出ができるよう…」は、書かれた時点では嘘だった（[B-32](#b-32) の一件）。**その /lint 相当を
> 実際に作ったので、コメントは実態の説明に書き換えた。**

<a id="b-44"></a>
**B-44: 装飾の中に書いたリンクが黙って消えていた** — 積んだその場で直したが、**見つかり方**のほうに
価値があるので記録を残す。

`parseInlineFormatting` が1パス設計で、`bold` の交替が内側の `[[…]]` ごと飲んでいた。
`**主張から [[原本と写し|原本]] まで、鎖を切らさない。**` と書くと、リンクは**ただの文字になる**。
`*斜体*` でも同じ。**パターンの「そこで」の一行目は結論なので太字にしたくなる** — 書き方の癖と
噛み合う場所に穴があった。実際に配布デッキの `patterns-llm-wiki/切れない鎖` で1本死んでいた。

**どの検査にも出なかった。** 死んだ参照は `collectRefs` に届かないので `broken` にも入らず、
サイドバーの未解決リンクにも CI にも出ない。lint も見ていない（[B-39](#b-39)）。
`stripInlineFormatting` は逆に中を剥がすので、**文字数だけは「原本」3文字で正しく数えられて**いた —
数え方と表示が食い違ったまま、どちらも赤くならない状態だった。

見つけ方は「書いた `[[…]]` の数」と「レイアウト段に届いた数」を突き合わせただけ
（237 対 234）。**この差分は他の項目にも効く物差しなので、冒頭の実測表に入れた。**

直したのは `matchToRuns` の再帰（`decorate`）で、装飾の中をもう一度走査して内側の run に
装飾を載せる。両レンダラは最初から bold+link を同じ run で扱えていた（HTML はリンクを最も外側で
包み、PPTX は `bold` と `hyperlink` を同じ options に載せる）ので、**欠けていたのはパーサだけ**だった。
内側に記法が無ければ run は分割されないため、既存のスナップショットは1つも動いていない。

**`*` と `**` は依然として互いに入れ子にできない**（`*` の交替が `**` を先に割るため、再帰しても
届く前に切り方が決まっている）。入れ子になったのはリンクとコードだけで、その線は
`inline-formatting.test.ts` が明示的に留めている — 「装飾が入れ子になった」と読まれると
別の期待が生まれるため。リンクの**ラベルの中**も再帰しない（`[[id|**強調**]]` の `**` はリテラル）。

<a id="b-01"></a>
**B-01: ドキュメント乖離の解消** — 個別に直すのではなく、乖離しうる事実の置き場を1つにした。
`ontology.yaml` が md の構造の正本になり、SKILL.md のレイアウト表・注釈表・インライン記法表・
文字数の記述は `gen-ontology-doc.ts` の生成領域になった（`--check` でドリフトを検出）。
文字数上限と各プラグインのディレクティブはコードから消え、`src/ontology/` 経由で宣言を読む。
`ontology.test.ts` が宣言 ⇔ 実装 ⇔ 生成物の3者を留める。
（残った手書きの数え上げは [B-32](#b-32)。）

<a id="b-02"></a>
**B-02: 箇条書きリスト対応** — マッチャはトークナイザではなく**ブロック層の
`parser/block-formatter.ts`** に置いた（`- ` `* ` `+ ` `N. ` を受理）。トークン層で拾わないので

<a id="b-24"></a>
**B-24: `--verify` の3者比較が壊れていた** — AST の脚が別のキー空間を使っていて、
`--verify` は食い違いを見つけても常に exit 0 だった（`Spec.md` で 400 件の偽陽性）。
直し方は「インベントリをインスペクタに合わせる」の**逆**を採った:

- **レンダラがキーを宣言し、インスペクタは数えずに読む。** 語彙は `src/shape-keys.ts` の1本で、
  PPTX は `objectName`（→ `<p:cNvPr name>`）、HTML は `data-shape-id` に同じ文字列を書く
- **比較対象はテキストを運ぶ図形だけ。** 境界ボックス・塗り・コード背景・SVG アイコンは
  `deco:` を付けて除外する（除外が生成物の中に書かれている状態にした）
- `--verify` は mismatch があれば**非ゼロ終了**。判定は `src/tools/verify.ts`

**併せて見つけて直した実バグ**（比較を直したから見えた。どれも PowerPoint 上の実害がある）:
絵文字アイコンに `fontFace` が無くテーマ既定フォントで描かれていた／改行を含む run を
そのまま渡すと最後の断片にも `breakLine` が付いて後続が1行下がる／末尾が改行の文字列は
pptxgenjs がまったく分割しない／`pptx-inspector` が実体参照をデコードしていなかった／
`html-inspector` の `font_name` が `"Arial"` のリテラルで `--theme` 使用時に食い違う／
コードテキストの座標が `padding` ぶんずれていた。

**共有すると比較では守れなくなる。** 3脚が同じ関数を呼ぶので、その関数が間違えば
3脚とも揃って間違い、`--verify` は緑のまま通る（実際、中央寄せの規則を壊しても全件通った）。
消した冗長性のぶんの検査は `text-style.test.ts` に置き直してある。
**共有モジュールを増やすときは同じ手当てが要る。**

残っている範囲は [B-33](#b-33)（何を保証していないか）と [B-34](#b-34)（見送った重複）。
