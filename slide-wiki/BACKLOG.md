# slide-wiki 機能バックログ

Markdown のデッキを**リンクで辿れるスライド Wiki** にする。同じデッキを PPTX と HTML にも出し、
座標は3系統で共通のレイアウトエンジンが計算する。このバックログは2つの軸で並べる —
**何が主題か**（Wiki が主題、PPTX と HTML は同じデッキの別の出し方）と、
**どう壊れるか**（黙って間違う > 見えて壊れる > 不便）。前者が band を分け、後者が band の中を並べる。
判断の根拠は[並べ方](#並べ方)にある。

**このファイルは「すぐやった方がよい」10件だけを持つ。** 残りは区分ごとに別ファイルにある —

[完了済み](BACKLOG-DONE.md)（11件）。**ID は4ファイルで1つの空間**で、再利用しない
（コード中の `BACKLOG B-NN` 参照が、畳んだあとも行き先を持ち続けるため）。

## 並べ方

改名のときは「Wiki が主題か、PPTX の話か」で並べ替えた。**主題の中での順位はまだ付いていなかった** —
Wiki の項目が P0 に3つ並んでいるだけで、どれが先かは書かれていなかった。今回の調査でその中身が
見えたので、band の意味を次のように決め直す。

| 区分 | band | 意味 |
|---|---|---|
| **すぐやった方がよい** | **P0** | **リンクの層**。この道具の看板そのもの。宣言・実装・報告の3つに分かれるが、直す対象は1つ |
| | **P1** | 主題を**実際に読み書きする人が踏む**もの。読めない・書けない・気づけない |
| **あとでやる**（[別ファイル](BACKLOG-LATER.md)） | **P2** | 読み書きする人には見えないが、直さないと**上の band が繰り返し生えてくる**土台 |
| | **P3** | 主題の外。やっても Wiki は良くならない（が、捨てるほどでもない） |
| **やらない**（[別ファイル](BACKLOG-WONTDO.md)） | — | 落とした理由ごと残す。ID は再利用しない |
| **完了済み**（[別ファイル](BACKLOG-DONE.md)） | — | 畳んだ要点を残す。コードの `BACKLOG B-NN` の行き先 |

**区分は band の上に被せた粗い線で、band を置き換えるものではない。** 着手の順は band が持ち、
区分が持つのは「いま読むべきか」だけ — **このファイルを開いた人が、他を開かずに
手を動かせる**ようにするために、区分ごとにファイルを分けてある。

順位を決めたのは主に**壊れ方**である。この調査で分かったのは、Wiki の層の不具合が
そろって「**黙って、動いているように見える形で**壊れる」ことだった —
リンクが生の文字で出る（[B-22](#b-22)）、リンクが**別のスライドに繋がる**（畳んだ [B-38](BACKLOG-DONE.md#b-38)）、
デッキが**どこにも書かれていない名前**になる（畳んだ [B-40](BACKLOG-DONE.md#b-40)）。どれも exit 0 で、lint も緑である。

**黙って間違う > 見えて壊れる > 不便**、の順に置いた。折れたリンク（[B-36](#b-36)）が
P0 の中で最後なのは、それが唯一**サイドバーに出る＝見える**壊れ方だからで、
軽いからではない。

## すぐやった方がよい

主題（リンクで辿れる Wiki）を**いま壊している**もの。順は band のまま — P0 が看板そのもの、
P1 が読み書きする人の手元。

### P0 — リンクの層（実装も報告も欠けている）

Wiki を主題にした以上、この道具の看板はリンクである。その層が、
**半分しか実装されておらず**（[B-22](#b-22)）、**ほとんど何も報告しない**（[B-39](#b-39) / [B-36](#b-36)）。
3件は別々の不具合ではなく、同じ1つの層の2つの面である。

> **この band は2回に分けて軽くなった。** 記法を OKF v0.2 に移した回で内部リンクが
> バンドル相対の絶対パス1本になり、4段階の解決順そのものが消えた
> （**書き方を1つに絞ると、規則のほうが要らなくなる**）。続く回で [B-41](BACKLOG-DONE.md#b-41) が
> `okf:` 節を立て、**宣言の欠落という面がまるごと落ちた** — 残りは実装と報告だけである。

**着手の順は重要度の順ではない。** 先にやるのは報告の2件（[B-39](#b-39) → [B-36](#b-36)）で、
どちらも lint と終了コードに1つずつ足すだけの作業。これを先に入れると
**B-22 が直すべき箇所を機械が列挙してくれる**（B-39 の診断がそのまま進捗メータになる）。
最後に [B-22](#b-22) の11プラグインに入る。

> 報告の3件目だった [B-38](BACKLOG-DONE.md#b-38)（明示 ID の衝突）は畳んだ。**着手して分かったのは、
> B-39 の「宣言は既にあるので安い」が成立しないこと** — `inline.effective-in` の
> `section-heading` / `section-body` は**リポジトリ全体でその宣言行にしか存在せず**、
> 読ませる先が無い。しかも宣言の内容自体が誤っている（Steps は `###` に `body: lines` を
> 宣言しているのにリンクは効かない）。効くかどうかは要素ごとではなく**スロットごと**なので、
> B-39 は「既にある宣言を読む」ではなく**新しい宣言軸を立てる**作業になる。
> 詳しくは [B-39](#b-39) 本文。

<a id="b-22"></a>
#### B-22: プラグイン内テキストのリンクが効かない

**背景**: リンクが効くのは `parseInlineFormatting` を通る箇所、すなわち `###` セクションの
見出し・本文と takeaway だけ。スライドタイトル、タイトルスライド、および11個のプラグインが
`layout.ts` で `text:` に直接書き出す箇所（table のセル、quote の本文、steps のラベル等）では
リンクが生の文字列として表示される。

**Wiki が主題になったので、これは表示の欠けでは済まない。** `renderer/wiki/link-graph.ts` の
`collectRefs` は `layoutSlide(...).textBoxes` だけを走査するので、プラグインが直接描いたテキストの
参照は**リンクグラフにも入らない**。つまり表示が生文字になるだけでなく、その参照先のスライドに
**バックリンクが立たない**。書いた本人は「繋いだつもり」でいて、サイトのどこにも繋がりが現れない。

表示側とグラフ側は**同時に直す**。片方だけ直すと、リンクは青くなるのに逆引きに出ない
（あるいはその逆）という、より分かりにくい状態になる。

**しかも黙る。** `collectRefs` が見ない以上、その参照は `broken` にも入らない —
未解決リンクの一覧にも CI にも出ない。lint も見ていない。書き手に届く信号は
**表示が生の markdown になることだけ**で、それはスライドを開いた人にしか分からない
（[B-39](#b-39) がこの穴を、直すまでの間だけ塞ぐ）。

**実装方針**: 各所の `text: X` を `richText: parseInlineFormatting(X)` に置き換える。
1行ずつの機械的な変更だが、PPTX/HTML のレンダ分岐が変わるため
`layout-engine.test.ts` のスナップショットと `snapshot-comparison.test.ts` の確認が要る。
`ShapeBox.text` は `richText` を持たないので、型の拡張が別途必要。

**受け入れ基準**: table のセルと quote の本文に書いたリンクが本当にリンクになり、
**同じ参照がリンク先のバックリンク欄にも現れる**。

**一部対応済み**: agenda は対応した（目次スライドでリンクが生のまま出ると
索引としてまったく機能しないため）。残りは table / quote / steps / icon-layout /
numbered-list / customer-journey / text-only / lean-canvas。

> この制限は `SKILL.md` と `ontology.yaml`（2箇所）が現時点の仕様として明記している。
> 直したらその3箇所も畳む。

<a id="b-39"></a>
#### B-39: 効かない場所に書いたリンクを誰も報告しない

**背景**: `ontology.yaml` の `inline` は `effective-in: [section-heading, section-body, takeaway]` と
**書く場所まで宣言している**。そして [B-28](BACKLOG-LATER.md#b-28) が挙げたとおり、`inline` は**誰も読まない宣言**である。
この2つが重なった結果、[B-22](#b-22) の範囲に書かれたリンクは**4つの経路すべてで見えない**:

| 経路 | 結果 |
|---|---|
| 表示 | 生の `[種](d.md#seed)` がセルに出る |
| リンクグラフ | `collectRefs` が見ないのでバックリンクが立たない |
| 未解決リンク | `broken` にも入らない（＝サイドバーにもCIにも出ない） |
| lint | ✅ 「宣言に沿っている」 |

実測（table のセルにリンクを1本置いたデッキ）: `--lint --strict` 緑、`--wiki` は
`backlinks: {}` / `resolve: {}` を吐き、HTML にはリンクの綴りがそのまま残る。
**書いた本人に届く信号がゼロである。**

**この穴を通り抜けた実例が [B-44](BACKLOG-DONE.md#b-44)。** 配布デッキに1本、太字の中に書いたせいで死んだリンクが
あったが、どの検査にも出ず、見つかったのは「書いた数と届いた数を突き合わせる」という
**この項目とは別の物差しを、たまたま1回だけ当てたから**だった。原因（1パス設計）は直したが、
**同じ穴に落ちる書き方は他にもある**（B-22 の範囲がまるごとそれである）。
恒常的に赤くする仕組みが要るのはそのため。

[B-22](#b-22) を直せばこの入力は正しく動くようになるが、B-22 は11プラグイン × レンダラ分岐の
作業で、着手までの間ずっとこの穴が開いている。恒常的に赤くする仕組みが要る。

**以前の版は「宣言は既にあるので、検査を足すのは安い」と書いていた。2026-08-10 の実測で
それが誤りだと分かった。** 2点ある。

1. **宣言の語がどこにも繋がっていない。** `section-heading` と `section-body` は、
   リポジトリ全体を grep して **`ontology.yaml` の `effective-in` のその行にしか存在しない**。
   `elements` が持っているのは `section` と `body`、Quote は `leading-body` という第3の語。
   読ませる先が無い3つの文字列である（[B-28](BACKLOG-LATER.md#b-28) の「誰も読まない宣言」の中でも、
   これは**読もうとしても読めない**という一段悪い形）
2. **宣言の内容が誤っている。** Steps は `slots: [{marker: "###", body: lines}]` を宣言していて
   `effective-in: section-body` に素直に当てはまるが、リンクは効かない（実測: steps / quote の
   本文に置いたリンクは生の文字で出て backlink も立たない）。さらに `agenda/layout.ts` は
   `###` 項目を `richText` で描く一方**スライドタイトルと副題は `text:`** で、
   同じレイアウトの中でも効く場所と効かない場所が混ざる。
   **効くかどうかは要素ごとではなくスロットごと**である

したがって、この項目は「既にある宣言を読む」ではなく**新しい宣言軸を1本立てる**作業になる
（17レイアウト × スロット、+ selfcheck で嘘を防ぐ）。畳んだ [B-41](BACKLOG-DONE.md#b-41) と同じ種類・同じ規模で、
「lint 1本で塞げる」という P0 昇格の根拠は成り立たない。**B-41 が済んだので足場は近くなったが、
足りないのは別の軸である** — B-41 が宣言したのはデッキをまたぐ層で、こちらが要るのは
レイアウトのスロットごとの層。

**実装方針は2案ある。**

- **(a) 宣言軸を足す**: 各 slot に「インラインが効くか」の印を持たせ、lint が読む。
  B-22 を直すたびに印を裏返す（診断が進捗メータになる）。宣言が正本という筋は通るが、
  **人間が17レイアウトぶん列挙するので漏れうる**
- **(b) 書いた数と届いた数を突き合わせる**（推奨）: [B-44](BACKLOG-DONE.md#b-44) を見つけた物差しの常設化。
  ソースのリンクと `collectRefs` が集めた参照を突き合わせ、差を「死んだ参照」として
  行番号つきで出す。**宣言が1行も要らず、列挙の漏れが原理的に無い** —
  B-22 の範囲も B-44 の装飾も、まだ知られていない第3の穴も同じ1つの検査で出る。
  [B-36](#b-36) と同じ「ビルド段で分かることを CLI まで運ぶ」配線に乗るので、
  報告経路は1本で済む

**(b) の引き換え**: リンクの解決は lint の2段下流なので `--lint` 単独では出せず、
`--wiki` の検査になる（CI が回るのはそちらなので、守りたい場所は守れる）。
また `guide.md` は記法の見本を**コード表記の中に置いている**ので、
数える前にインラインコードを剥がさないとこの2本が恒久的な誤検出になる
（冒頭の実測表の「235 / 237」の差がまさにこれ）。

**受け入れ基準**: table のセルに書いたリンクが行番号つきで報告される。
`###` 本文に書いたものは報告されない。B-22 で対応済みの agenda の `###` も報告されない。
`guide` の記法見本は報告されない。

<a id="b-36"></a>
#### B-36: 折れたリンクがビルドを止めない

**背景**: `buildLinkGraph` は解決できなかった参照を `broken`（`not-found` / `ambiguous`）に集め、
`template.ts` がサイドバーの `<details>`「未解決リンク N 件」に並べる。**それだけである。**
CLI は何も言わず exit 0 で終わる（実測: 存在しないリンクを含むデッキで exit 0・標準エラー空）。

**CI だけは止まる。ただし止め方が生成物の日本語の grep である。** `pages.yml` の
「Fail if the wiki has unresolved links」は `grep -q "未解決リンク" _site/index.html` で判定する。
`template.ts` の `<summary>` の文言を変えた瞬間に grep が空振りし、**空振りは「0件」と同じ
exit 0 になる**ので、ガードが外れたことに誰も気づけない。検査が守っている当の対象
（`renderer/wiki/template.ts`）を編集すると検査自身が黙って消える構造で、
これは検査として成り立っていない。折れたリンクを載せた Wiki が公開される経路は、
ローカルでは常に、CI では文言を触った瞬間から開いている。

`--lint --strict` はこれを拾えない。lint はディレクトリを丸ごと受け取れる（実際 8 デッキを
一度に検査している）ので、範囲の問題ではない。**層の問題である** — `lint.ts` が見ているのは
トークン層（「消えたブロックは AST に痕跡を残さない」から）だが、`collectRefs` が読む
`InlineTextRun.link` は**レイアウト段で初めて載る**。リンクの解決は lint が立っている場所の
2段下流にある。したがって折れを検出できるのは `--wiki` のビルド時だけで、その唯一の場所が
黙っている。

（`resolveRef` の3段目が「サイト全体でちょうど1つ」を条件にしていることも効く —
デッキが1つ増えただけで、いままで解決していた参照が `ambiguous` に変わりうる。
デッキ単位で1回検査して済ませられる性質のものではない。）

現時点の `doc/wiki`（5デッキ・52枚）は 0 件。**いま緑なので、赤くする仕組みを入れるなら今が安い。**

**実装方針**: `--wiki` に `--strict` を効かせ、`broken` が1件でもあれば
一覧を標準エラーに出して非ゼロ終了する。既定は現状どおり警告（外部の md をそのまま
流し込む使い方を殺さないため）。CI の publish は `--strict` を付け、**grep のステップは消す**
（残すと「二重に守っている」ように読めるが、実際に守るのは exit code のほうだけになる）。

**受け入れ基準**: 存在しないリンクを1つ足すと `--wiki --strict` が非ゼロで落ち、
`fromId → /deck.md#id` が読める形で出る。
`pages.yml` に生成物の文言を読むステップが残っていない。

> **`broken` に入らない折れ方がある。** [B-22](#b-22) の範囲（プラグインが直接描くテキスト）に
> 書いたリンクは `collectRefs` が見ないので、リンクにならないだけでなく
> **未解決リンクとしても数えられない**。この項目を入れても、そこは緑のままである
> （見えるようにするのは [B-39](#b-39)）。

### P1 — 読めない・書けない・気づけない

読み手がサイトから何も引けない（[B-37](#b-37) / [B-42](#b-42)）、書き手が宣言どおりに書けない

（[B-32](#b-32) / [B-07](#b-07)）。P0 と違って一本の層ではないが、
**どれも「主題を実際に読み書きする人が踏む」ところにある。**

<a id="b-37"></a>
#### B-37: 絞り込みが本文を見ていない

**背景**: サイドバーの絞り込みが照合する `data-search` は
`` `${entry.title} ${entry.globalId}`.toLowerCase() ``（`renderer/wiki/template.ts:21`）、
つまり**スライドの題と ID だけ**。本文・節見出し・takeaway は入っていない。

Wiki は「読み終えたところから、また入り直す」ための道具で、入り直す手がかりは
たいてい本文の中の語である。題を覚えていないと辿り着けないのは、索引としての取りこぼしが大きい。
現時点で5デッキ・52枚あり、目次を上から眺めて探すのは既に実用的でない。

**ブラウザの検索も効かない。** `.wiki-slide { display: none }`（`styles.ts:205`）なので、
`Ctrl+F` が見ているのは**いま表示している1枚だけ**である。つまりこのサイトには
**本文を引く手段が1つも無い** — 絞り込みは題と ID しか見ず、ブラウザの検索は78枚を見ない。
「本文も見る絞り込み」は便利さの追加ではなく、唯一の全文検索を用意する話になる。

**一部実装済み（デッキ単位）**: デッキの frontmatter が名乗る `description` と `tags` は
`data-search` に流れるようになった（`site-index.ts` が畳み、`template.ts` が混ぜる）。
実測で `ナレッジマネジメント` 0→11枚、`出典` 0→16枚、`第2部` 0→26枚が引けるようになり、
**79枚を7つの意味の束に切る**ところまでは効いている。
残っているのは**スライド1枚ごと**の絞り込みで、以下はその話。

**実装方針**: `data-search` に本文のプレーンテキストを足す。
`layoutSlide(...).textBoxes` からテキストを集める経路は
`link-graph.ts` の `collectRefs` と同じなので、走査を1本にまとめて両方に使う。
サイトが自己完結（外部リソース禁止）なので、索引は HTML に埋め込む。
分量が問題になるなら、まず「節見出し + takeaway まで」の中間案がある。

**受け入れ基準**: 本文にしか現れない語で、そのスライドが絞り込みに残る。
生成 HTML のサイズが実用の範囲に収まる（`wiki.test.ts` の自己完結性テストは引き続き通る）。

<a id="b-42"></a>
#### B-42: 孤立したスライドを誰も数えない

**背景**: `buildLinkGraph` は `forward`（どこへ出ているか）と `backlinks`（どこから来ているか）の
両方を作る。`backlinks` はビューアに渡って「このスライドへのリンク」欄になる。
**`forward` は `WikiSite` に載るだけで、どこからも読まれない**（利用者は `wiki.test.ts` だけ）。

被リンクゼロのスライド — 目次から選ぶ以外に辿り着けないスライド — は、
その `backlinks` に鍵が無いことで**既に分かる状態にある**のに、数える場所が無い。実測:

| 内訳 | 件数 |
|---|---|
| 全スライド | 47 |
| 被リンクゼロ | 5 |
| └ デッキの表紙 | 5（構造上そうなる。除外してよい） |

初回の実測（79枚だった頃）では `guide` の本文4枚が本当に孤立していた。**機能ガイドという、
いちばん最初に読ませたいデッキが、サイトの中では誰からも指されていない。** 想定問答
（`questions.yaml`）を敷いた回に再測すると `intro-wiki` の本文2枚も孤立しており、
どちらも `map` の索引から指して解消した。ただし**数える場所が無い事情は変わっていない** —
手で作った索引が全スライドを網羅しているか確かめる手段が無いので、デッキを足すたびに
同じことが起きる（今回の6枚は、実測した人が数えたから見つかっただけである）。

このサイトが載せているパターンのほうが先に言っている — `けもの道` は「踏まれた道を索引にする」、
`剪定` は「繋がっていないものを見つけて畳む」。**道具が自分の載せている物差しを自分に当てていない。**

**実装方針**: `--wiki` の出力に「被リンクゼロ N 枚」を出す（既定は情報、`--strict` でも
落とさない — 孤立は誤りではなく手入れの合図なので、[B-36](#b-36) の折れリンクとは扱いを分ける）。
表紙（`deckIndex === 0` の TitleSlide）は数えない。サイドバーにも `<details>` で
未解決リンクの隣に並べると、手入れの入口が1箇所に揃う。
`forward` はここで初めて使い道が出る（「出るリンクがゼロ」＝行き止まりも同じ欄で出せる）。

**受け入れ基準**: `--wiki` が孤立したスライドの一覧を出す。表紙は含まない。
今日の時点で本文の孤立は0だが、それは手で数えて手で塞いだ結果なので、
次に孤立が生まれたとき（デッキを足したとき）に一覧へ出ることがこの項目の本体。

<a id="b-26"></a>
#### B-26: 文字数の数え方が宣言に反する

**背景**: `ontology.yaml` の `limits.counts` は
「本文と見出し（Markdown 構文を除く）。**リンクは表示ラベルだけを数え、URL は数えない**」と宣言する。
正本の `countPlainTextChars`（`schema/validation.ts`）はそのとおり `stripInlineFormatting` を
通し、リスト記号も落とす。

ところが同名の関数が**6つのプラグインの `index.ts` にコピーされている**
（agenda / icon-layout / lean-canvas / numbered-list / steps / wiki-pattern）。
いずれも `stripInlineFormatting` もリスト記号除去も持たない弱い版で、`#`・`<!--…-->`・
空行しか落とさない。結果、**URL とリスト記号がそのまま文字数に入る**。
2026-08-08 の調査時点では5つだった — **新しいプラグインが増えるたびに写しが増えている。**

再現（同一の本文、リンク1本、URL は 1200 文字強）:

| 入力 | 結果 |
|---|---|
| `### 見出し` + `[ラベル](長いURL)`（Default） | ✅ 生成成功 |
| `<!--lean-canvas-->` + `### 課題` + 同じ本文 | ❌ `ValidationError` `charCount: 1230` |

宣言では両者とも「ラベル3文字」のはずで、レイアウトを変えただけで通らなくなるのは
オントロジーが約束していない挙動。**Wiki のデッキはリンクを多く張るので、この差は日常的に踏む。**

**実装方針**: `registry.getCharCounter` がプラグインから受け取るのは「どのフィールドを数えるか」
だけにして、正規化は `validation.ts` の `countPlainTextChars` 1本に寄せる。
プラグイン側のコピーを削除する。

**受け入れ基準**: 同じ本文は、レイアウトの `max-chars` が同じなら同じ文字数になる。
上の URL ケースを回帰テストにする。

<a id="b-27"></a>
#### B-27: lint の盲点（タイトルスライド・`slot.body`）

**背景**: lint がトークン層を見ているのは「消えたブロックは AST に痕跡を残さない」から
（`lint.ts` 冒頭）。その設計意図に対して、**黙って消える2つの経路が検査されていない**。

1. **タイトルスライドを一切検査しない**。`detectLayout` は `##` を持たないトークン列に
   `undefined` を返し、`lintTokens` はそこで `continue` する。実測: タイトルスライドに書いた
   `### 未宣言の見出し` + 本文は出力から消えるが `--lint --strict` は「✅ 宣言に沿っている」を返す。
   宣言側は `annotations[].applies-to` に骨格要素を持っているのに、lint は `layouts[].annotations` しか
   参照していないので、この情報が使われていない
2. **`slots[].body` の `free｜lines｜bullets-only｜none` が未強制**。
   `gen-ontology-doc.ts` が文書に印字するだけで、誰も照合しない。
   実測: カスタマージャーニーの `#### タッチ` 直下に非箇条書きの行を書くと
   `customer-journey/handler.ts` の `if (!token.text.startsWith('-')) return` で捨てられ、
   HTML にも PPTX にも現れないが `--lint --strict` は緑

**実装方針**: (1) `detectLayout` が undefined を返す断片にも、TitleSlide 用の宣言
（`elements.title-slide`）を当てて注釈スコープと未宣言 `###` を見る。
(2) `slot.body` を lint の検査項目に加える（`bullets-only` の slot 配下で `- ` 以外の
BodyText を warning）。

**受け入れ基準**: 上の2ケースが `--lint` で警告になる。既存デッキが引き続き
`--lint --strict` を通る（通らないものが出たらデッキ側の実バグ）。

<a id="b-32"></a>
#### B-32: 存在しない保証を主張しているコメント・数え上げ

**背景**: 「乖離しうる事実の置き場を1つにした」あとも、**保証の所在についての記述**が
乖離している。これは普通のドキュメント誤りより悪い — 読んだ人が「守られている」と信じて
チェックを足さなくなる。

**予言していた失敗が実際に起きた。** `selfcheck` は `レイアウト 17 / プラグイン 12` と言うのに、
`SKILL.md:24` と `CLAUDE.md:14` の「**16レイアウト**」は生成領域の外の手書きのままで、
17個目（wiki-pattern）が入った時点で黙って嘘になった。`docs-consistency.test.ts` が
見ているのは `10ディレクトリ` / `11プラグイン登録` だけで、この2文は無防備。
CLAUDE.md 自身が「そちらにある内容をここへ写さない（写した瞬間、四重管理とドリフトが始まる）」と
書いている、その直後の行で写している。

**同じ失敗がもう1件、Wiki の説明の中で起きている。** `SKILL.md` は配布サンプルのデッキ数を
散文で数え上げていて、デッキを足したり削ったりするたびに手で直す必要がある
（実際 `patterns-meta` を足したとき・LLM の2デッキを削ったときの両方で取り残された）。
`docs-consistency.test.ts` はプラグイン数・テストファイル・レイアウト件数を照合するが、
デッキ数は見ていない。`order.yaml` が正本になりうるので、突き合わせ先はある。

他:

- `plugins/lean-canvas/layout.ts` の `findCellIndex` のコメントが
  「その `key` は上の `LEAN_CANVAS_CELLS` の `name` と対応する（**selfcheck が両者を突き合わせる**）」
  と書くが、**`selfcheck.ts` は lean-canvas を import していない**。実際に守っているのは
  `ontology.test.ts` の描画テスト。書き換えるべきは保証の名前
- ~~`renderer/wiki/link-graph.ts` の `collectRefs` のコメントが「1スライドにつき
  `layoutSlide` が2回走る」と書くが、実際は3回~~ → **直した**（`buildLinkGraph` /
  `buildResolutionTable` / 描画の3回と明記）。数え間違いそのものは無害だが、
  この数字は「許容する」判断の損益分岐を記録したものなので、そこだけは合っている必要がある
- **コード中の `BACKLOG B-NN` 参照を誰も照合していない**（10箇所ほどある）。
  実例: [B-25](BACKLOG-DONE.md#b-25) の作業で `ci.yml` に書いた残件の参照が、直後に項目を分けた時点で
  古い ID を指したままになった（同じコミット内で気づいて直した）。
  `docs-consistency.test.ts` に「`src/` ・`__tests__/` ・`.github/workflows/` ・docs の
  `B-NN` が `BACKLOG.md` のアンカーに解決すること」を足せば安い8割は取れる。
  **ただしアンカーの存在だけでは足りない** — 上の実例はアンカーが実在する
  完了済み項目を指していた。「残件だと書いている参照が完了節を指していないこと」まで
  見るのが本来の形

**実装方針**: コメントを実際のガード（`ontology.test.ts`）の名前に直すか、selfcheck に
本当に照合を足す（[B-29](BACKLOG-LATER.md#b-29) のコアレイアウト照合と同じ作業になる）。
レイアウト件数は `gen-ontology-doc.ts` の生成領域に入れるか、`docs-consistency.test.ts` で
宣言の件数と突き合わせる。

**受け入れ基準**: コードコメントが主張する保証が全て実在する。レイアウト件数を1つ増やすと
テストが赤くなる。デッキを1つ足しても同じく赤くなる。

<a id="b-07"></a>
#### B-07: 固定要素数レイアウトの柔軟化

**背景**: IconColumn / IconCard は TypeScript の tuple 型で **3要素固定**（2個や4個は型エラー）。
CustomerJourney も4行固定。**4件以上書くと4件目以降が黙って捨てられ、2件以下だと黙って Default に
落ちる** — どちらも警告が出ない。Claude が生成するコンテンツは必ずしも3項目に収まらず、
機械的生成の入力制約として厳しすぎる。

**実装方針**: tuple を長さ2〜4の配列 + バリデーションに変更し、レイアウト側
（`plugins/icon-layout/layout.ts` 等）で要素数に応じた幅・フォントサイズ計算を行う
（Grid の `calculateGridSpacing` と同様の段階縮小）。可変化しないなら、
せめて**捨てるときに lint が言う**のが最低線。

**受け入れ基準**: `<!--icon-cols-->` で2〜4項目が均等配置される。3項目の既存スナップショット
テストが変化しない（後方互換）。

> `ontology.yaml` がこの制限を現時点の仕様として明記している。直したらそこも直す。

#### B-48: 「人が書き、AI が手入れする」を本文が語っていない

**背景**: `patterns-wiki` の description（表紙とサイドバーに出る一文）は
「人が書き、AI が手入れする」と分担を掲げるが、**AI の側の仕事を語るスライドが1枚も無い**。
バンドル全体で AI への言及はこの一文だけである。想定問答を敷いた回
（`doc/wiki/questions.yaml`）に「AI は具体的になにを手入れするのか」を問いとして立てたところ、
答えのアンカーを書けず `expect: gap` として置くしかなかった — この gap がこの項目の証跡で、
問いのほうがバンドルより先に正直になっている。

看板の半分が本文に無いのは、読み手には**約束と違うもの**が届いているということである。
人の側は10パターンが語っている（置く・割る・繋ぐ・束ねる…）。AI の側 — 剪定の候補出しか、
接ぎ木の相手探しか、けもの道の踏み跡の集計か — は書いた人の頭にしか無い。

**実装方針**: AI の手入れを語る一枚（またはパターン）を書く。文体が練られたパターン集への
加筆なので、**機械的修繕とは分けて人の執筆判断に委ねる**。書けたら
`questions.yaml` の当該の問いに `answers` を書いて `expect` を answered に上げる
（上げ忘れは answerability.test.ts が gap の整合として見ている）。
逆に、この一文のほうを変える（分担を掲げない）判断もあり得る — その場合も gap の問いを畳む。

**受け入れ基準**: 「AI は具体的になにを手入れするのか」が `expect: answered` になり、
実走評価（`docs/answerability-eval.md`）でエージェントがそのアンカーへ辿り着く。
