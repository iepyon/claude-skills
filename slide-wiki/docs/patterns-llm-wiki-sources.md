## 対応関係

このデッキの2枚は、DDD の2つのパターンに正面から対応する。

| このデッキ | DDD | 検証度 |
|---|---|---|
| 名寄せ | Ubiquitous Language（ユビキタス言語） | ○ |
| 縄張り | Bounded Context（境界づけられたコンテキスト） | ○ |

順序も同じで、**ユビキタス言語が一貫するのは境界の内側だけ**である。だから
`縄張り` が `名寄せ` の前提になり、デッキでも `判子`（境界を先に決める）の内側に置いた。

## 名寄せ ○

**一次**: Evans, *Domain-Driven Design: Tackling Complexity in the Heart of Software*
(Addison-Wesley, 2003) の **Ubiquitous Language**。ドメインエキスパートと開発者が
同じモデルに基づく1つの言語で話し、その言語を会話・図・コードのすべてで使う。
用語の揺れを翻訳で埋めるのをやめ、言語のほうを1つに寄せる。

**刻んだ文**: 「チーム全員が同じモデルに基づく1つの言語で話し、用語の揺れを
会話にもコードにも残さない」。要約であって逐語引用ではない（一次資料の本文が未読なので、
引用符では書けない）。

**名前は DDD 由来ではない。** 「名寄せ」は名簿・顧客台帳の実務語で、同じ相手を指す
複数の表記を1件に束ねる作業を指す。`借りてきた比喩` に従って借りた語で、**原著には無い**。
スライドにもその一文を刻んである。

## 縄張り ○

**一次**: 同書の **Bounded Context**。広く引用されている定義文は
"Explicitly define the context within which a model applies. Explicitly set boundaries
in terms of team organization, usage within specific parts of the application, and
physical manifestations such as code bases and database schemas."
（二次資料が Evans の原文として引くもの。**本文は未読なので ○**）

**刻んだ文**: 「モデルが適用される文脈を明示的に定義し、チーム編成・コードベース・
スキーマの形で境界を引く。ユビキタス言語が一貫するのは、その内側だけである」。
前半はこの定義文の要約、後半は上の対応関係のほう（Evans 2014 の DDD の定義
"Speak a ubiquitous language within an explicitly bounded context" と同じ主張）。

**名前は DDD 由来ではない。** 「縄張り」はこのデッキの借り物。

### false cognate は刻まなかった △

同じ語が2つの文脈で別のものを指す状態を Evans が **false cognate**（空似言葉）と
呼んで警告している、という説明が二次資料に複数ある。ただし **一次資料でこの語を
確認できていない**（原文のどの節にあるのか、Evans 自身の語なのか、後から
コミュニティが付けた呼び名なのかが分かれない）。

このデッキの `縄張り` の場面はまさにこの現象なので刻みたくなるが、
**確認できていない系譜を 6pt で印刷すると、後から剥がせない**。だから
スライドには出さず、ここに未確認として残す。◎ に上げられたら本文に足す。

---

## 刻まなかったもう1つの線

`名寄せ` の「決めるのは人」「変えるときは判子」は、DDD では Ubiquitous Language の
運用（言語の変更はモデルの変更である）に当たるが、**AI に寄せさせて人が承認する**という
分担そのものは DDD には無い。このデッキの追加なので、出典には書いていない。
