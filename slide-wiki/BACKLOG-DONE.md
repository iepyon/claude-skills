<a id="b-41"></a>
**B-41: サイトの階層が宣言に無かった** — `ontology.yaml` に `okf:` 節を足した
（版 4 → 5）。バンドルの根・予約ファイル名・デッキ集合と `order.yaml`・deck slug の
作り方・ID の一意性の範囲・`okf_version` が宣言に入り、`ontology.md` と SKILL.md の
6つ目の生成領域に出る。**宣言の輪郭が主題より1段小さい状態は解消した。**

**効いたのは「規則を写すか、例を写すか」の判断だった。** deck slug の作り方は
`slugify` の5段の連鎖 replace で、宣言に散文で書けば必ず写しになる。**写しは照合できない。**
そこで規則そのものは書かず、`deck-slug.rule` が**在り処を指すだけ**にした
（`src/slug.ts` が「綴りが1つであることは両側が同じ規則で作られる保証そのもの」と
書いている、その保証を宣言の側でも壊さないため）。**書かない判断を `guidance` に
理由つきで残した** — 次に読む人が同じ問いに当たるので。

予約名と版は**導出せず双方向で照合する**（`layouts[].plugin` ⇔ registry と同じ形）。
`okf.ts:9-11` は以前から「ここに置くのは綴りだけで、規則の説明は ontology.yaml が持つ」と
書いていたが、**その ontology.yaml 側が無かったので、書かれた時点では嘘だった** —
[B-32](BACKLOG.md#b-32) が数えている「存在しない保証の主張」の実例が、これで1件減る。
`ontology.test.ts` の3本（予約名・`OKF_VERSION`・`DECK_ORDER_FILE`）が縛る。
実際に `RESERVED_OKF_FILES` へ1つ足して赤くなることを確かめてから戻した。

**積んだときの「4箇所」の数え上げは間違っていた。** 実測すると `doc/wiki/guide.md` には
予約名も OKF も1度も出てこない（guide が持つのはリンクの**形**だけ）。4つ目は
`ontology.yaml` 自身で、`internal-link` の `guidance` が「**この2つの名前はまだ宣言に無く、
`src/okf.ts` がコードで持っている**（B-41）」と自分で告白していた。しかも
`types.ts` の `InlineSyntax` に `guidance` フィールドが無いので、**その告白は
`ontology.md` に一度も出ていなかった** — [B-28](BACKLOG-LATER.md#b-28) の「誰も読まない宣言」の中でも、
書いたのに読ませる先が無いという一段悪い形である。**散文の重複はコードの重複より多い**、
というのが実測の結論（コード側のリテラル重複は `gen-okf-index.ts` の出力先1箇所だけだった）。

<a id="b-40"></a>
**B-40: デッキ名が2つの語彙を持っていた** — `order.yaml` の照合を生のファイル名から
**デッキ slug** に揃え、slug の衝突を連番ではなく誤りにした。`slugify` の直接呼び出しは
`okf.ts` の `deckSlug()` 1本に畳んだ（呼んでいたのはパイプライン・`order.yaml` の照合・
リンクの解決・移行ツールの4箇所で、**割れていたのはまさにこの4箇所の間**だった）。
衝突の判定も `migrate-wikilinks.ts` が持っていたものを `findDeckSlugCollisions` へ移した。

**着手して見つかったのは、照合が3箇所目にもあったことだった。**
`gen-okf-index.ts` の `buildIndex` が `order.yaml` の名前を**生ファイル名**で引き、
引けなければ黙って落として「その他」の節へ回していた。`orderDeckFiles` だけを
slug 照合にしていたら、**宣言が通ったデッキが目録から静かに消える** — B-40 と同じ
壊れ方を、直す側が作るところだった。「1つの語彙に寄せる」変更は、
**寄せ残した1箇所が新しい沈黙になる。**

止める場所は `cli.ts` の作法（「誤りは返す。終わらせるかどうかは呼び手が決める」）に従い、
`orderDeckFiles` は誤りを返して `collectOrExit` が exit 1。API 経由（`md2wiki`）は
デッキを1本も読む前に `ValidationError` で落ちる。**入口を2つとも塞いだのは、
ディレクトリを渡す経路と md を名指しする経路が別々にあるから**で、片方だけだと
もう片方が素通しになる。`site-index.ts` の `unique()` は**残した** — `buildWikiSite` を
直に組み立てる呼び手が居るので、外すと「黙って別名」より悪い**重複した globalId** が出る。

**衝突の検査は `order.yaml` の有無に関わらず走る。** 衝突は宣言の誤りではなく
ディレクトリの誤りなので、宣言が無いときだけ黙るのは筋が通らない。
あわせて誤りの所在を `deck-order.ts` 側へ移した — 呼び手が一律に前置していたので、
**`order.yaml` が無くても起きる誤りにまで `order.yaml:` と付いて、実在しない
ファイルを指していた。**

**既存のサイトは1バイトも変わっていない。** 配布バンドルの5デッキ名はいずれも
`slugify` が恒等写像になる綴りなので、生成 HTML を変更前後で `diff` して同一を確認した
（理屈ではなくバイト一致で取った）。`doc/wiki/index.md` も動いていない。

<a id="b-46"></a>
**B-46: 記法が Obsidian 由来のままで、LLM Wiki の標準から外れていた** —
`[[…]]` は Obsidian の綴りで、`inline-formatter.ts` のコメントが自分でそう名乗っていた。
一方 Google Cloud の [Open Knowledge Format v0.2](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md)
は、まさにこの道具がやっていること —「YAML frontmatter を持つ md のディレクトリで
知識を持ち回る」— を標準化していて、**`[[wikilink]]` に一言も触れていない**。
§6.1 が規定するのは通常の markdown リンクだけで、推奨形はバンドル相対の絶対パスである。

つまり「LLM Wiki の作り方を教えるスキル」が、その標準から外れた独自方言で書かれていた。
`ontology/types.ts` は既に `OKF 同様、未知のキーは保存して拒まない` と OKF を
引き合いに出しており、片足だけ突っ込んだ状態だった。

**畳み方として効いたのは「書き方を1つに絞ると、規則のほうが要らなくなる」ことである。**
内部リンクを `/デッキ名.md#スライドID` の1本にしたら、4段階あった解決順が1段になり、
「候補が2つあって決められない」という失敗モードが**原理的に消えた**（型からも落とした）。
[B-41](#b-41) が数えていた「3箇所に手書きされた解決順」は、解決順ごと無くなっている。

238箇所の書き換えは `src/tools/migrate-wikilinks.ts` が行った。**表示テキストを
1文字も変えない**ことを不変条件にしてあり、変換前後の md 1437 行を
`stripInlineFormatting` で突き合わせて差 0 を確かめた — そのぶんレイアウトの
スナップショットも3者比較も動いていない。ツールは同梱して残す（他人のデッキを
受け取るスキルなので移行路が要る。旧記法の綴りと4段階の解決順は、いまやこのファイルだけが持つ）。

frontmatter は、キー名がもともと OKF と同名のものが多く、ずれていたのは値の形だった
（actor の接頭辞・`at` が RFC3339）。`index.md` / `log.md` は予約名なのでデッキから外し、
目録は `order.yaml` の `groups:` から生成する。`category` などの独自キーはそのまま残した
— OKF が「知らないキーは保存して拒まない」と定めているので、拡張が通ること自体が適合の裏返しになる。

実装は `src/okf.ts`（予約名とリンクの形の正本）・`src/tools/gen-okf-index.ts`、
検査は `__tests__/okf-conformance.test.ts`（§11 の3条件をそのまま並べたもの）と
lint の `legacy-wikilink` / `link-form`。**「準拠した」を誰も確かめていない言葉にしない**
ためのもので、これが無いと次にデッキを1本足した人が黙って外れる。

<a id="b-25"></a>
**B-25: 型検査が CI にもテストにも無かった** — 直したのは2つで、**大きいのは後者**である。

**型検査**: `tsc --noEmit` の3件は `schema/theme.ts` の配列型テーマ値
（`iconCardAccentColors` / `stepsColors` / `badgeColors`）で、原因は `DeepPartial` が
**配列にも再帰していた**こと。`string[] extends object` が真なので要素まで省略可能になり
`(string | undefined)[]` が出て `Theme` に代入できなくなっていた。配列を再帰から外して解決。
意味としてもそれが正しい — パレットの3要素目だけを部分上書きする操作に意味は無く、
穴の空いた配列を許すと描画側が `undefined` を色として受け取る。
`package.json` に `typecheck` を足した（vitest は esbuild で型を捨てるので `npm test` では出ない）。

**CI**: こちらが本体だった。`pages.yml` のトリガは `main` への push と手動だけで、
**PR では検査が1つも走っていなかった**。積み上げてきた検査 — selfcheck・生成物の鮮度・
宣言に照らしたデッキの lint・3者比較・[B-38](#b-38) の `slide-id` — は全部
`npm test` の中にあり、**「人が手元で打つこと」だけに依存していた**。壊れたデッキを載せた PR は
マージして `main` のビルドが落ちるまで分からず、そのとき deploy も止まるので
サイトが古いまま残る。

**`pages.yml` に PR トリガを足すのは誤りである。** あのファイルは
`concurrency: {group: pages, cancel-in-progress: true}` を単一グループで持っており、
以前そこに PR の run が混ざったとき、後から始まった PR 側が push 側を殺して
デプロイが消えた（当該コメントに記録がある）。したがって**別の workflow**
（`.github/workflows/ci.yml`、PR で `npm test` + `npm run typecheck`）を立て、
concurrency group も別にした。

**その教訓をテストにした。** コメントは次にワークフローを足す人を止められないので、
`workflows.test.ts` が「公開が `pull_request` で走らないこと」と
「2本の concurrency group が重ならないこと」を落ちる形で留める
（どちらも実際に退行させて赤くなることを確認した）。このサイトが載せている
`実行可能な規約` を、ワークフローの側でも守った形。

残っているのはテストコードの型検査（[B-45](BACKLOG-LATER.md#b-45)、38件）。`gen-ontology-doc --check` と
`selfcheck` を npm スクリプトにしないのは意図的で、どちらも `ontology.test.ts` が
走らせている — CLI をもう一度叩くと二重管理になる。

**触らなかったこと**（書かない除外は「守られている」と読まれるので挙げておく）:
lockfile を追跡しない方針はそのままにした。そのため CI は毎回 `npm install` で依存を
再解決し、`npm ci` より **1回あたり約3.3秒**遅い（実測 9.2秒 対 6.0秒）。
さらに `~/.npm` のキャッシュキーが `package.json` のハッシュだけなので、
**キーが完全一致する限り `actions/cache` は保存し直さない** — キャレット範囲が
新しい推移的依存に解決されるほどキャッシュは冷えていき、上限で1回あたり約7秒失う
（冷 16.3秒 対 温 9.2秒）。直すなら lockfile を追跡して `npm ci` +
`setup-node` の `cache: npm` にするのが筋で、`pages.yml` と `.gitignore` に跨る
方針変更なので分けた。

<a id="b-38"></a>
**B-38: 明示した ID の衝突が黙って別の ID になっていた** — 報告を足すだけの項目として積んだが、
**採番の規則そのものに穴があった**ので両方を直した。

積んだときに書いていたのは「同じ `<!--id:seed-->` を2枚に書くと2枚目が黙って `seed-2` になる」で、
これは実測どおりだった（`--lint --strict` 緑・`--wiki` exit 0・サイトの ID は `dup/seed` と
`dup/seed-2`）。**折れたリンクより悪い**のは、`[[seed]]` が**解決してしまう**ことである — 常に1枚目へ。
2枚目は誰からも指されないスライドとしてサイトに残り、未解決リンクの一覧にも出ない。

**着手して見つかったのは、衝突がもう1種類あることだった。** `unique()` は自動 slug と明示 ID を
区別しないので、**自動 slug が明示 ID に勝つ**:

```markdown
# 設計                    ← 表紙。slugify("設計") が先に `設計` を取る
---
## 設計の考え方
<!--id:設計-->            ← 書き手が明示した。しかし `設計-2` に降格される
```

`[[設計]]` は表紙に着き、バックリンクも表紙に立つ。lint 緑、exit 0。**勝敗が md の並び順で
決まる**ので、無関係なスライドを1枚前に足しただけで既存のリンクの行き先が変わりうる。
`<!--id:-->` は書き手が「この名前で指す」と宣言する唯一の手段なのに、**予約として機能していなかった**。

**もう1つ、`unique()` は重複した ID を出しうる状態だった。** 連番を「その base が何度目か」の
カウンタで決めていたので、`## X-2` が先にある状態で `## X` が2枚続くと、2枚目が `x-2` を
再発行して1枚目と衝突する（サイトのリンクが解決できなくなる）。

直したのは3点:

- **明示 ID を予約として扱う**（`parser/slide-ids.ts`）。変換を先に済ませて明示 ID の集合を
  作り、自動 slug はそこを避けて連番に回る。**`[[…]]` の行き先が md の並び順に依らなくなった**
- **連番は「その綴りが空いているか」で決める**。カウンタをやめたので重複が出ない
- **明示 ID 同士の衝突は lint が報告する**（`ontology/lint.ts` の `slide-id`）。一意化そのものは
  続ける（重複するとリンクが解決できない）。どちらが間違っているかは機械に決められないので、
  両方の行番号を出して書き手に返す。自動 slug が押さえられた側にも「この見出しの ID は
  `設計-2` になる」と伝える

検査をトークン層に置けたのは、**ID の一意性がデッキ内で閉じている**ため（`site-index.ts` が
`deck-slug/` を前置する）。lint は1ファイルずつ呼ばれるので、検査の範囲もそのまま合った。
**サイトの階層の宣言（[B-41](#b-41)）を待つ必要が無かった**のはこの1点による。
取り逃がすのは1ブロックが複数スライドを生む場合の派生 ID（`--2`）の衝突だけで、
何枚生まれるかはトークン層の2段下流でしか分からない。

**既存の ID は1枚も変わっていない**（`doc/wiki` の79枚を採番の前後で突き合わせ、順序込みで一致）。
配布デッキには予約が絡む衝突が1件も無く、`Spec.md` の同名見出し2枚だけが自動 slug の連番
＝正しい振る舞いのケースだった。`slide-id.test.ts` が予約・並び順非依存・重複の不発行を、
`ontology.test.ts` が診断の行番号と「タイトルが同じだけの2枚は報告しない」を留めている。

> `slide-ids.ts` のコメントが主張していた「明示 ID の衝突も黙って解決せず、あとで /lint 相当の
> 検出ができるよう…」は、書かれた時点では嘘だった（[B-32](BACKLOG.md#b-32) の一件）。**その /lint 相当を
> 実際に作ったので、コメントは実態の説明に書き換えた。**

<a id="b-44"></a>
**B-44: 装飾の中に書いたリンクが黙って消えていた** — 積んだその場で直したが、**見つかり方**のほうに
価値があるので記録を残す。

`parseInlineFormatting` が1パス設計で、`bold` の交替が内側の `[[…]]` ごと飲んでいた。
`**主張から [[原本と写し|原本]] まで、鎖を切らさない。**` と書くと、リンクは**ただの文字になる**。
`*斜体*` でも同じ。**パターンの「そこで」の一行目は結論なので太字にしたくなる** — 書き方の癖と
噛み合う場所に穴があった。実際に配布デッキ（当時あった `patterns-llm-wiki/切れない鎖`）で1本死んでいた。

**どの検査にも出なかった。** 死んだ参照は `collectRefs` に届かないので `broken` にも入らず、
サイドバーの未解決リンクにも CI にも出ない。lint も見ていない（[B-39](BACKLOG.md#b-39)）。
`stripInlineFormatting` は逆に中を剥がすので、**文字数だけは「原本」3文字で正しく数えられて**いた —
数え方と表示が食い違ったまま、どちらも赤くならない状態だった。

見つけ方は「書いた `[[…]]` の数」と「レイアウト段に届いた数」を突き合わせただけ
（237 対 234）。**この差分は他の項目にも効く物差しなので、冒頭の実測表に入れた。**

直したのは `matchToRuns` の再帰（`decorate`）で、装飾の中をもう一度走査して内側の run に
装飾を載せる。両レンダラは最初から bold+link を同じ run で扱えていた（HTML はリンクを最も外側で
包み、PPTX は `bold` と `hyperlink` を同じ options に載せる）ので、**欠けていたのはパーサだけ**だった。
内側に記法が無ければ run は分割されないため、既存のスナップショットは1つも動いていない。

**`*` と `**` は依然として互いに入れ子にできない**（`*` の交替が `**` を先に割るため、再帰しても
届く前に切り方が決まっている）。入れ子になったのはリンクとコードだけで、その線は
`inline-formatting.test.ts` が明示的に留めている — 「装飾が入れ子になった」と読まれると
別の期待が生まれるため。リンクの**ラベルの中**も再帰しない（`[[id|**強調**]]` の `**` はリテラル）。

<a id="b-01"></a>
**B-01: ドキュメント乖離の解消** — 個別に直すのではなく、乖離しうる事実の置き場を1つにした。
`ontology.yaml` が md の構造の正本になり、SKILL.md のレイアウト表・注釈表・インライン記法表・
文字数の記述は `gen-ontology-doc.ts` の生成領域になった（`--check` でドリフトを検出）。
文字数上限と各プラグインのディレクティブはコードから消え、`src/ontology/` 経由で宣言を読む。
`ontology.test.ts` が宣言 ⇔ 実装 ⇔ 生成物の3者を留める。
（残った手書きの数え上げは [B-32](BACKLOG.md#b-32)。）

**B-02: 箇条書きリスト対応** — マッチャはトークナイザではなく**ブロック層の
`parser/block-formatter.ts`** に置いた（`- ` `* ` `+ ` `N. ` を受理）。トークン層で拾わないので
`*italic*` と衝突しない。PPTX は `bulletToPptxOption` でネイティブバレット、HTML は
`.para-bullet` / `.para-number` を CSS 疑似要素で描く（リテラルの `•` は書かない）。
効くのは `buildSectionBoxes` を通る経路だけ — 届かない範囲は [B-22](BACKLOG.md#b-22) と同じ。

<a id="b-08"></a>
**B-08: オーバーフロー処理の一般化** — 2段構えで入った。`dispatchLayout` が
`contentSlide` 系のフォントサイズを 0.9 → 0.6 と段階的に下げて再レイアウトし、
それでも収まらなければ `validateLayout`（`renderer/layout/validate-layout.ts`）が
スライド番号と理由つきの `ValidationError` でビルドを止める。`validateLayout` は
**レイアウトを問わず全スライドを走査する**ので、「黙ってはみ出したまま出荷」は起きない。
`overflow.test.ts` が検出・縮小・失敗の3経路を見る。

<a id="b-14"></a>
**B-14: ハイパーリンク対応** — 想定より広く実装した。フィールド名は `hyperlink` ではなく
`link`（`{kind:"external"|"internal"}` の判別共用体）で、外部 URL と `[[slide-id]]` の内部リンクが
同じ経路に載る。PPTX は外部が `hyperlink:{url}`、内部が `hyperlink:{slide:N}`
（`ppaction://hlinksldjump`）。解決できない内部リンクはリンクを付けない。
文字数カウントは表示ラベルのみ（`stripInlineFormatting` に一本化）。
**副産物がスライド ID と `--wiki` 出力**（`renderer/wiki/`）で、いまの主題はここから出た。
残っている範囲は [B-22](BACKLOG.md#b-22)。

<a id="b-24"></a>
**B-24: `--verify` の3者比較が壊れていた** — AST の脚が別のキー空間を使っていて、
`--verify` は食い違いを見つけても常に exit 0 だった（`Spec.md` で 400 件の偽陽性）。
直し方は「インベントリをインスペクタに合わせる」の**逆**を採った:

- **レンダラがキーを宣言し、インスペクタは数えずに読む。** 語彙は `src/shape-keys.ts` の1本で、
  PPTX は `objectName`（→ `<p:cNvPr name>`）、HTML は `data-shape-id` に同じ文字列を書く
- **比較対象はテキストを運ぶ図形だけ。** 境界ボックス・塗り・コード背景・SVG アイコンは
  `deco:` を付けて除外する（除外が生成物の中に書かれている状態にした）
- `--verify` は mismatch があれば**非ゼロ終了**。判定は `src/tools/verify.ts`

**併せて見つけて直した実バグ**（比較を直したから見えた。どれも PowerPoint 上の実害がある）:
絵文字アイコンに `fontFace` が無くテーマ既定フォントで描かれていた／改行を含む run を
そのまま渡すと最後の断片にも `breakLine` が付いて後続が1行下がる／末尾が改行の文字列は
pptxgenjs がまったく分割しない／`pptx-inspector` が実体参照をデコードしていなかった／
`html-inspector` の `font_name` が `"Arial"` のリテラルで `--theme` 使用時に食い違う／
コードテキストの座標が `padding` ぶんずれていた。

**共有すると比較では守れなくなる。** 3脚が同じ関数を呼ぶので、その関数が間違えば
3脚とも揃って間違い、`--verify` は緑のまま通る（実際、中央寄せの規則を壊しても全件通った）。
消した冗長性のぶんの検査は `text-style.test.ts` に置き直してある。
**共有モジュールを増やすときは同じ手当てが要る。**

残っている範囲は [B-33](BACKLOG-LATER.md#b-33)（何を保証していないか）と [B-34](BACKLOG-LATER.md#b-34)（見送った重複）。
